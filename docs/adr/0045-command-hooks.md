# ADR 0045: External Command Hooks (Claude/Codex Subset)

Status: accepted

## Background

`radian-core` owns only in-process `Hooks` traits (`before_tool_call` refuses/rewrites/answers directly, errors fail closed, ADR 0012 P2/P3, ADR 0017 §4). Users and projects mount no outer commands. Claude Code hook JSON is a de-facto standard (event names, `matcher`, `hooks[{type:"command",command,timeout}]`, exit 2, `hookSpecificOutput`), Codex adopts it unchanged. Its importer takes only a fidelity-safe subset (`type` must be `command`, `allow`/`ask` always refused). Radian tool and parameter names differ from Claude (`shell`/`write`/`patch`/`read` versus `Bash`/`Write`/`Edit`/`Read`). No runtime aliases exist. Translation runs once in import commands only.

## Decisions

### 1. Four events, two layers

Only `PreToolUse`, `PostToolUse`, `Stop` and `PermissionRequest` exist. `PostToolUse` runs post-edit lint and similar. `Stop` validates at turn end. Failed validation opens the next turn automatically. `PermissionRequest` runs inside the permission layer's `ask` branch (§4): it answers a call the rules already judged `ask`, never a `deny` and never an allowed call. No `async`, `if`, `http`, `prompt`, `agent` style handlers exist, and no more events exist.

Config writes the Claude/Codex JSON subset directly. Both layers stay isomorphic. User level is the `config.toml` `[hooks]` section (TOML writes the same shape). Project level is `<workspace>/.radian/hooks.json` (JSON writes the same shape directly). Top level holds event names. It also takes one `{"hooks": …}` wrapped form. Event names map to `{ matcher, hooks }` entry lists, then each hook `{ type = "command", command, args, timeout }`. `args` is optional; §4 holds its exec-form rule. `matcher` takes Claude case-sensitive patterns. It matches only **Radian** tool names. `*` or empty/absent matches all. Else regexes match whole tool names (`^(?:<matcher>)$`). So `Edit|Write` and `Notebook.*` work. `sh` never matches `shell`. Illegal patterns warn one row at load, and those entries never run (never warn per call). `Stop` ignores it. Outside-the-subset items skip entry by entry with one row each. Items are unknown event names, broken entries, hooks with `type` other than `command`, entries carrying any of `async`/`if`/`http`/`prompt`/`agent`. User level logs `skipped`, named with the startup row. Project level warns with the `[hooks]` startup row. Layers **never** refuse files.

Project-level `<workspace>/.radian/hooks.json` enters the ADR 0031 trust gate: trusted directories load, with no per-content hash confirms. Later-changed files load new content directly at next startup, with no new questions. `--trust` overrides this process. Mid-session changes take effect at next startup. Untrusted projects never read files and never run project hooks, and startup rows state it as-is.

Both layers stack by these rules:

1. Both layers run, and project layers never turn off or replace user-layer hooks.
2. Project first, user last. `updatedInput` passes to each next hook in turn. Project rewrites are the parameters user hooks see. Rewritten Core only rechecks rights, never reruns hooks (ADR 0012 P3). User hooks run last. They see the final soon-to-run parameters. Repo rewrites never route around them. `PostToolUse` with `Stop` follows the same order.
3. Hooks with fully equal `command` and `args` in one event run once (both layers writing one command and its arguments never runs twice). The same program with different arguments is two hooks.
4. `Stop`: both layers exiting 2 opens only one continuation turn, causes merge into one message, counts one wake.
5. `PermissionRequest`: project first, user last. Any layer's `deny` stops the chain, later hooks never run. No `deny` and at least one `allow` allows the call. No decision anywhere leaves the ordinary path. Item 3's dedupe applies: the same `command` and `args` run once across the layers.
Refusal stays: any layer refusing stops the chain, later hooks never run (refusals only narrow).

### 2. stdin, exit codes, and JSON

Child stdin uses Claude field names: `hook_event_name`, `tool_name`, `tool_input`, `tool_response` (only `PostToolUse` owns it, the whole `ToolResult`), `cwd`, `session_id`. `cwd` is the session workspace, `session_id` is the current session. `PermissionRequest` carries the `PreToolUse` fields — `hook_event_name`, `tool_name`, `tool_input`, `cwd`, `session_id` — and no `permission_suggestions`: radian's permission rules are types, not text, so there is nothing to suggest. `Stop` additionally carries `last_assistant_message` (a Claude field name). It holds text parts of the turn last assistant message joined together. Empty string means none. Users detect with their own scripts.

`Stop` also always carries three more fields, so a script can tell "really done" from "waiting" and can see a continuation it is inside of:

- `stop_hook_active` (bool, always present, default `false`): `true` when this turn was opened by a `Stop` continuation — a hook exit 2, its JSON equivalents, or the built-in validator. The continuation is a queued followup carrying its own message id; the turn that claims that message reports `true`, and no `Stop` run for another turn reads or clears the value. A user message (`followup`, `steer`, `inject`) drops a continuation still waiting to be claimed, so the turn that later claims it reports `false`; a turn that already started keeps its value. This is the same reset point as the wake budget.
- `background_tasks` (array, always present, `[]` when none): the background jobs running when `Stop` runs, from the session's job registry. Each entry is `{ "id", "type": "shell", "status": "running", "description", "command" }`: `description` is the command's first line and `command` the full command. A missing or dropped registry reads as `[]`.
- `session_crons` (array, always present, `[]` when none): the session-level schedulers that open turns by themselves. `/loop` on adds `{ "id": "loop", "type": "loop" }`; an `Active` or `Paused` goal adds `{ "id": "goal", "type": "goal", "status": "active" | "paused" }`. `radian exec` has no loop, so it can carry only a goal entry.

- exit 0: continues. Empty stdout means nothing. Non-empty parses as Claude JSON on `PreToolUse`, `PostToolUse` and `Stop`: `hookSpecificOutput.permissionDecision: "deny"` refuses (meaningful only for `PreToolUse`; `PostToolUse` and `Stop` warn once and ignore it). `updatedInput` (object) replaces tool parameters. Only `PreToolUse` `updatedInput` takes effect, becoming `ToolDecision::Rewrite` (rechecks, never reruns hooks, ADR 0012 P3); `Stop` warns once and ignores it. Non-JSON stdout warns and ignores (exit-0 hooks succeed, with nothing to fail closed on). `PostToolUse` and `Stop` also read:
  - `hookSpecificOutput.additionalContext` (string): non-error feedback. `PostToolUse` appends `[PostToolUse hook] <text>` to that result **without** setting `is_error`. `Stop` opens one continuation through the exit-2 chain: the same wake gate, merged with every exit-2 verdict and the built-in validator into one message, one turn, one wake. It is not a hook error and warns nothing.
  - `decision: "block"` with `reason`: the JSON equivalent of exit 2 with stderr. `PostToolUse` appends the reason and marks the result an error; `Stop` continues. When `additionalContext` is given too, both texts enter, block first.
  - `hookSpecificOutput.updatedToolOutput` (string, `PostToolUse` only): replaces the result content with one text part, keeping `is_error` and `error_code`. A non-string value fails closed as a hook error.
  All three truncate to 2000 characters (`REASON_CHAR_LIMIT`), like stderr.
- exit 2: `PreToolUse` refuses calls with stderr as cause (`denied`). `PostToolUse` feeds stderr back to the model. Feedback appends after those results, marked wrong. Tools already ran, with nothing left to refuse. Both layers exiting 2 appends one each, project first. `Stop` continues turns with stderr. Inside budget takes `System` `followup` opening new turns. Topped rate gates degrade to `inject` (injects only, never wakes). Three visible signals follow (journal `degraded` marks, one TUI notice row, herdr `wake budget`). Window passing or user-message-woken turns absorb waiting injections, degrade counts clear with them. Empty stderr takes one fallback line, never stays empty. Both layers exiting 2 merges causes into one message, opens one turn only, counts one wake (decision 1 item 4).
- Other exit codes or timeouts (default 60 s): hook errors, fail closed (ADR 0017 §4). `PreToolUse` refuses (`hook_error`), `PostToolUse` swaps results to `hook_error`, `Stop` never continues turns and warns one row only.

`PermissionRequest` is the one event whose exit-0 JSON decides. `hookSpecificOutput.decision.behavior` is `"allow"` or `"deny"`; `decision.message` (string, optional) is the text of a deny result (reason code `denied`) and is ignored on allow. A missing or unknown `behavior` warns one row and means no decision. Empty stdout or no `decision` means no decision: the ordinary path follows — the approver on a human turn, the denial on a non-human turn or a terminal-less `radian exec`. Exit 2 denies with stderr as the reason. Any other exit, a timeout, or exit-0 stdout that is not JSON fails closed as `hook_error`, and never falls back to asking a human. `decision.updatedPermissions` is ignored silently in this version; `decision.updatedInput` and `decision.interrupt` are ignored with one warning row. Layers follow decision 1 item 5.

`"allow"`/`"ask"` are refused **on `PreToolUse`** (same Codex caliber, ADR 0012 P1 "never widens"). Imports warn one row and handle them as "no decision". `PermissionRequest` is the exception: its `allow` answers a call the rules already judged `ask`, so it removes a question rather than widening a decision. A `deny` rule, an allowed call and the sandbox are untouched.

### 3. `Stop` continuations

`Stop` continuations take no separate switch once enabled. Continuations share rate rules with background notices. Rules are ADR 0037 decision 5: max 10 continuations per 10-minute sliding window, fixed, no config keys. Counts stay separate. Continuations take the inbox `followup` lane (`System` source, non-human, ADR 0011 L2). Idle wakes one turn, busy waits for turn end, same shape as background notices (ADR 0037 decision 5). Woken turns absorb waiting injections, degrade counts clear with them. User-message arrival (any of `followup`/`steer`/`inject`) clears immediately too.

The chain also counts consecutive idle hook continuations: a continuation a hook opened (exit 2, `decision: "block"`, `additionalContext`) whose turn ended `Completed` with no tool call (`model_calls == 1`). A continued turn that called a tool resets the count to zero, and so does a non-`Completed` turn (the same reset point as the validator's streak) and a user message (any of `followup`/`steer`/`inject`). At 8 (`MAX_HOOK_IDLE_CONTINUATIONS`) the continuation does not open a turn: it moves to `inject` marked `degraded` (journal-visible), one TUI notice line shows, and herdr reports `blocked` with category `hook stop`, never body text. The stop lasts until a user message or the next turn start. The 10-per-10-minute window stays the hard cap, and the validator's own two-in-a-row rule stays separate and unchanged. A hook and the validator merging into one turn count once in each counter.

The continuation point is the host `Hooks` `on_turn_end`. Core calls once per turn end (after `RunFinished`). Only `RunStatus::Completed` runs `Stop` hooks. Cancelled, failed, budget, exhausted, refused, poisoned, and all other end states never run. User-cancelled exit-2 hooks never open new turns. Non-`Completed` also clears built-in validator streak counts. The host starts one async task above it running `Stop` hooks, once globally per turn. Past-cap hooks still run: exit 2 never opens new turns, moves to `inject` (never wakes) marked `degraded`, and conclusions wait for next turns (user-message-woken ones, or window-passing-woken ones). Three visible signals match background-notice degrades (decision 2 TUI notices with herdr `wake budget`). Woken turns absorb waiting injections, degrade counts clear with them. User-message arrival (any of `followup`/`steer`/`inject`) clears immediately too.

The same chain also carries one built-in validator, sharing chains, gates, and degrade visibility with user `Stop` hooks. No configured `Stop` hooks still runs it. `[hooks] intent_stop = false` turns it off (user hooks still run). Triggers are turns ending `Completed` with last assistant messages hitting conservative rules. Pure text, no tool calls. Whole text caps near 200 chars. Sentence ends own no question marks. No asking-human patterns of the "want me to / let me know / tell me / need me" kind exist. Last sentences start with gerunds. They take `Now`/`Next`/`Then`/`Let me`/`I'll`/`I will`/`Time to`, or "next / now / then / next-step" openers. `Nothing` counts as no gerund. Hyphen-joined words are one token, never word starts. Action subjects exclude `you`/`p1`/`lead` (either language). No background jobs run at end. Open `/loop` or `/goal` never triggers (they resubmit their own turn ends). `exec -p` behaves the same as TUI. Rules only roughly screen, and models own judgment. Hits send one fixed-wording `System` `followup` (`Your last message announced a next step but made no tool call. If the task is not done, continue now. If it is done, or you need the user, say so in one line.`). They set `meta` `continuation = "intent-stop"` (ADR 0005). False hits cost one short call plus one transcript row, and never do unplanned things.

Hits merge with hook exit 2 into one continuation: max one per turn. Causes merge into one message (hook causes first, fixed wording last), counting one wake. Validator-joined messages carry `intent-stop` origin (pure hook continuations carry none). Two straight continuations still ending in hitting pure text never continue a third time. They never wake. They move to `inject` (`degraded`, journal-visible). One TUI notice row shows. herdr reports `blocked` (H2-class `blocked` messages, category `intent stop` only, never body text). Blocks last until user messages or next-turn starts. Missed rules, turned-off switches, `/loop` or goal-owned turn ends, running jobs all clear streak counts. User-message arrival clears too.

### 4. Sandbox and chain order

`workspace`-tier hook children take the same sandbox build and env rules as `shell` tools. With no `args`, builds use `command_str("/bin/sh", ["-c", …])`. With `args`, `command` is an executable (a path or a `PATH` name) and the hook starts directly with exactly those arguments, never through a shell: `sandbox.command_str(command, args)` in a sandboxed slot with the same env rules, `Command::new(command).args(args)` with no sandbox. An empty `args` array is a run with no arguments. `setsid` and the timeout's process-group kill are unchanged. An `args` that is not an array of strings skips that hook only, with one warning line, and the entry's other hooks still load. Non-forced backends pass env allowlists the same. `full` owns no sandbox (slots with no sandbox start the hook directly, inheriting host env).

The implementation is one `radian-host` `Hooks` (`CommandHooks`), never changing `radian-core` traits. It orders **after rights** in `session_hooks` (`role → permissions → commands → memory → skills → facts`). Rights-refused calls stay invisible to hooks. Hooks only narrow rights-passed calls. **Hooks are no safety bound**. Invalid config entries skip instead of refusing files (decision 1). Misspelled `PreToolUse` rows never run. Forced policy lives only in rights rules (ADR 0012) and sandboxes (ADR 0016). Hooks only narrow above them. `Rewrite` semantics hold through tuple composition: earlier `Rewrite` rows are the parameters later rows see.

`PermissionRequest` is not a second layer after rights: it runs **inside** the permission layer's `ask` branch, after the rules, the policy and any session grant produced `ask`, and before the approver and the non-human-source denial. `radian-permissions` owns the seam (the `PermissionRequestHooks` trait); `radian-host`'s `CommandHooks` implements it and `open_session` installs it, so the two crates do not depend on each other. An `allow` only removes the question: the same sandbox and `deny` rules still apply, and `PreToolUse` still follows (it can deny or rewrite the allowed call).

### 5. Where hook output enters context, and when

`PreToolUse` refusal causes enter those call error results. `updatedInput` never enters context (it is the parameters themselves). `PostToolUse` exit-2 feedback and `additionalContext` write synchronously right after **those edited tool results**, before those calls return. An `updatedToolOutput` replacement also happens there, before `ToolExecutionSettled`: the journal and the transcript hold the replaced result. The project layer replaces first, and the user layer receives the replaced result on its own `tool_response`. Runs stay sync, once per edit. Cross-turn segment deferred merges never happen. Background runs never happen. Post-edit checks are a **project-level setting**. They run only when project `.radian/hooks.json` configures `PostToolUse` entries hitting edit tools. Trusted directories only (see decision 1). Unconfigured means nothing happens and no child processes start. Radian ships no language check commands built in, and never auto-enables on repo `Cargo.toml`, `tsconfig.json`, or similar. User-level `[hooks]` works as usual, but repos own what checks run. `Stop` continuation stderr and `additionalContext` are next-turn input, never past-turn content. Hook stderr and the exit-0 feedback fields truncate to 2000 chars before entering transcripts.

## Constraints and Costs

- Non-JSON hook output only warns, never fails closed. Exit-0 hooks succeed by definition. Fail-closed belongs to "unfinished" (non-zero/timeout), never "misspoken".
- `Stop` "once per turn" rests on Core `on_turn_end` calls. Core skipping those calls some day disables continuations. Chain-order tests with Stop count tests guard the host side, and `radian-core` own tests guard Core-side calls.
- Sandboxes read most of `$HOME` (ADR 0012 P4). Hook-readable things stay out of model reach this turn. Hook stdout/stderr enters transcripts. Never print sensitive-dir content into hook output.
- User-level hooks take effect directly (user own commands). Project-level hooks load and run only in trusted directories (ADR 0031 T1). Untrusted directories never read files and never start processes.

## Verification

`hooks` unit tests cover entry by entry: exit-2 refusal with causes, `deny` refusal, `allow` non-import (warns plus still follows rights), `updatedInput` rewrites (non-objects fail closed), Post exit-2 feedback, timeout fail-closed, matcher misses never run, `wri.*` hits with `sh` missing `shell` (unanchored matchers fail the latter), illegal patterns warn once and never run, outside-sandbox write failures, Stop continuation minute-level chains never degrade, second-level fast loops stop continuing after 10 (window passing restores with no user message, user messages clear), Stop runs only on Completed (cancelled/failed turns exit-2 never opens new turns; all-states-run fails cancel tests), consecutive idle hook continuations degrade at 8 with the inject, the notice and the `blocked` category while a tool-calling continued turn resets the count (a dropped cap or a dropped reset fails), order tests (rights-refused calls never run hooks, `allow` still asks approval). `PermissionRequest`: an exit-0 `allow`/`deny` decides (the deny message reaches the denied result), empty/unknown output leaves the ordinary path, a non-2 exit/timeout/non-JSON stdout fails closed, the stdin carries the tool fields and no `permission_suggestions`, the project layer runs first and any layer's deny stops the chain, an identical command runs once, `updatedPermissions` is ignored silently and `updatedInput`/`interrupt` warn, a deny rule or an allowed call never fires it, a session grant never fires it, a non-human turn is answered, and cancelling kills the hook's process group (a dropped guard leaves the hook running fails). Project-layer unit tests: user hooks receive project-rewritten `updatedInput` (swapped layer order fails), one command written in both layers runs once (dropped dedup fails), both layers exiting 2 opens one turn only with causes in one message counting one wake (two turns fail), any-layer refusal stops later hooks, unconfigured project `PostToolUse` leaves post-edit results as-is (no child processes), configured runs sync once per edit with project feedback first, untrusted project files never load (loading fails). Built-in validator unit tests: fixed samples (the stalls labeled in `research/2026-10-21-intent-stop.md` §4.1 with false-hit classes plus about 20 plain turn ends, asserting labels entry by entry; dropped validators fail plain entries), hit continuations with no hooks (early returns fail), `Done.`/questions/waits (jobs running)/`Next: …` never continue (dropped rules fail), hook exit 2 merging with hits in one turn (split turns fail), two straight continuations never continuing a third with `blocked` reports (dropped caps fail), non-Completed never running with cleared counts (all-states-run fails), gate-full degrades (gate-skipping runs fail), `Stop` stdin holding `last_assistant_message`, turned-off switches never running, `/loop`/goal/running-job scenes never running. Mutation checks: open `allow`, ignore `updatedInput`, drop rate gates, drop matcher anchors, drop sandboxes, run Stop on all states, swap layer order, drop dedup, open two turns on two-layer exit 2, load project files untrusted, drop validator rules, drop once-per-turn, drop two-straight caps, gate-free validator continuations, drop the idle-continuation cap, keep no-hook early returns. Named tests must fail each. Exec form: `args` reaches the program verbatim (`;`, `$(…)`, spaces, `*`), runs inside the workspace sandbox, dedup keys on `command` plus `args`, a bad `args` drops only its hook, and a missing command records `failed to start`; the last two mutations (shell-routing an `args` hook, keying dedup on the command alone) must fail them.
