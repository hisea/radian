# ADR 0048: arc, the Plan and Task Orchestrator

Status: accepted

## Background

Today a lead session dispatches work to radian workers through herdr panes, and a person runs the gate and the merge by hand. The lead writes briefs, watches panes, and copies tips between branches. This work is slow, and it fails when a message is lost or a pane stops.

arc replaces this loop. arc is a deterministic program, not a model. It keeps a backlog of plans and tasks on disk, starts one headless radian worker for each task, runs a fixed gate on the result, and merges only what passes. ADR 0043 keeps radian to one session kind with no in-process orchestration. arc does its work across processes: each worker is a separate `radian exec` process with its own journal.

## Decisions

### 1. Commands

arc is part of the `radian` binary (ADR 0032). It is not a separate program.

```text
radian arc                    open the arc TUI
radian arc <subcommand>       run one CLI operation and exit
```

- `radian arc` with no subcommand opens the TUI. A subcommand runs the CLI. This follows `radian` (TUI) and `radian exec` (headless). The TUI's pages are `plans`, `board`, `task` and `merge`; they read the plans, the tasks, the attempt verdicts, a worker's journal and a task's diff, and the owner's keys act through the same library calls as the CLI (decision 11). The `board` groups the open tasks of the plans the plans page's view shows by who acts next (`todo`, `doing`, `verifying`, `needs you`), and `d` opens a finished list; `b` opens it from any page. The `merge` page is enabled for a task in `review.*` or `done`.
- The CLI subcommands are `init`, `add`, `list`, `show`, `adopt`, `start`, `merge`, `reject`, `auto`, `priority`, `confirm`, `pause`, `reset-budget`, `cancel`, `reverify`, `run`, `serve`, `mcp`, and the two internal ones a person does not run, `work` and `gate`. `mcp` takes `--claude-experimental` (boolean, default off): with it the server pushes task transitions to the lead over Claude Code's channel extension, and without it the server is exactly the server above and sends no notification (decision 11).
- Exit codes: 0 success; 1 error; 2 usage error; 3 the state does not allow the operation (this includes a file changed outside arc); 4 a lock is held by another process. `list` takes `--all` and `--json`; `show` takes `--json`.
- `start` is the owner's run-now command: it claims a `todo.ready` task or a `todo.retry_wait` one, without consulting `retry_at` (decision 9).
- `rad arc` is the same command through the `rad` alias.

### 2. Roles

- **lead**: a model session (Claude Code or the radian TUI). It analyzes a request, writes the plan and the tasks, and writes rework briefs. It writes to the backlog only through the `radian arc mcp` tools. It cannot confirm, start, merge, or approve.
- **arc**: the only writer of the backlog. It claims tasks, starts workers, reconciles attempts, checks delivery, runs the gate, records cost, and merges.
- **worker**: one process for one attempt of one task: `radian exec`, or the command `[worker] command` names (decision 7). It has no interactive input. It exits when the attempt ends.
- **gate**: a fixed sequence of stages. Each stage runs once against one commit and writes one verdict.
- **owner**: the person. The owner confirms plans, starts tasks, merges, rejects, sets the auto level, and sets the plan's priority. The owner acts in the arc TUI or on the arc CLI, never through MCP.

### 3. Objects

arc has four objects.

| Object | Meaning | Created by | State changed by |
|---|---|---|---|
| Plan | One product request: the request text, its tasks, and their order | lead | owner (confirm, cancel, auto, pause, priority); arc |
| Task | One unit of work in one plan, with a brief | lead; arc (the review's follow-up) | arc |
| Attempt | One run of one task | arc | arc |
| Verdict | One gate stage result for one commit | gate | nobody: a verdict is never changed |

- A plan has `status` `draft`, `confirmed` or `cancelled`. A plan is **finished** when it has at least one task, every task is `done.merged` or `failed.cancelled`, and at least one task is `done.merged`; a plan with no tasks is never finished. `done` is not a stored status. A plan whose tasks are all `failed.cancelled` is **cancelled**, exactly as a plan whose `status` is `cancelled`: the rule is derived from its tasks, and the plan file's `status` is not rewritten. Both rules live in `radian-arc`, next to each other, and every reader uses them: `list` and its `--json` form, the arc TUI's views, and the plan mark.
- A cancelled plan is final. Nothing confirms it, gives it a task, changes its `auto` or `priority`, resets its budget, or starts, reverifies or gates its tasks; `radian arc cancel` itself refuses a plan that is already `cancelled` (exit 3). `list` hides a cancelled plan (whether its `status` says so or all its tasks are `failed.cancelled`) and `list --all` shows it, the text form and `--json` alike; `show` still reads the plan and its tasks.
- After a plan is confirmed, its request text can only get appended change records. The text is never rewritten, because rework briefs use it as context.
- To change a confirmed plan, the lead appends a change record. The plan returns to `draft` with `auto` `off`, the lead adds any new tasks with `add_task`, and the owner confirms the plan again; tasks that already started keep their state. A cancelled plan takes no change record.
- A confirmed plan does gain **proposed tasks**. The lead's MCP `add_task` on a confirmed plan creates a task in `todo.proposed`, and arc proposes one follow-up task for a plan whose last open task is gone (decision 10). A proposed task belongs to the plan, but the scheduling loop never claims it and `start` refuses it; the owner makes it `todo.ready` with `radian arc confirm <task>`, which leaves the plan's `status` and `auto` alone. An owner who does not want it cancels it with `radian arc cancel` and it becomes `failed.cancelled`.
- A task has a `plan` field and an `after` list. `after` can name tasks in the same plan or tasks that are already merged.
- A plan has a `priority`: `P0`, `P1`, `P2`, `P3`, `P4` or `P5`, where `P0` is the highest. A plan file without the field reads as `P3`, and arc writes the field only once the owner sets it. A task has no priority of its own; it follows its plan. `radian arc priority <plan> <P0..P5>` sets it on a plan that is not `cancelled`, and refuses a value outside the set with exit `3` and a message that lists every value. There is no MCP tool for it: like `confirm` and `auto`, it is the owner's.
- A plan has no branch. arc merges each task separately.

### 4. Identities

- `plan_id` and `task_id` have the form `<PREFIX><NNNN>-<slug>`, like ADR file names with a kind prefix. The prefix is 1 to 4 ASCII uppercase letters: `[ids] plan_prefix` for a plan (default `PL`) and `[ids] task_prefix` for a task (default `TK`) in `config.toml`; the two must differ, and a prefix that is empty, not 1 to 4 uppercase letters, or equal to the other is refused by name when the config is read. The lead gives the slug: `[a-z0-9-]`, 1 to 48 characters. arc gives the number: plans and tasks count in separate sequences again, and a new id takes the next free four-digit number above the highest number any item of that kind (a file or a ledger entry) uses, whatever prefix that item carries. A well-formed id is any prefix of 1 to 4 uppercase letters, then four digits, a dash and a slug; an id without a prefix is not well-formed (exit 2). The kind comes from the directory the id is looked up in (`plans/` or `tasks/`), not from the prefix, so an item created under an earlier prefix keeps working after the prefix changes. An id names one item: every command that takes a plan or task id refuses (exit 3) an id that names both a plan file and a task file, naming both paths, and changes nothing. The id is the file name and never changes.
- `session_id` is the worker session of the attempt. `[worker] rework_session` decides its shape: `fresh` (the default) gives every attempt a session of its own, `<task_id>-<attempt>`, the shape the review sessions use, and the wrapper never resumes one; `resume` gives the task one session, whose id is `task_id`, which the first attempt that reaches the model creates and every later attempt (a retry or a rework) resumes with `--resume`. No session is ever forked (ADR 0022).
- `attempt_id` is `<task_id>-<n>`. Each attempt records its host, a random token, the worker process identity (pid and start time), its worktree, its branch, `base_sha`, `head_sha`, its start and end time, and its session id. The claim writes the session id it decided on to `attempts/<task>/<attempt>/start.json`, and the wrapper writes the session it used to `identity.json` and `execution.json`. A reader takes the first record that has it: `execution.json`, then `identity.json`, then `start.json`; only an old attempt, or a worker-less `reverify` attempt, has none.
- The claim also writes the worker it decided on to `start.json` as `worker`, `{"kind": "command", "flow": …, "program": …}` or `{"kind": "radian", "flow": …}`, and the wrapper writes the worker it started to `identity.json` and `execution.json` in the same shape. A reader takes the first record that names a worker, in the same order. A task's `flow` takes effect at the next claim, so the worker and its flow are a property of the attempt: a reader that classifies a running attempt uses its record and never the configuration, which may have changed since the attempt was claimed.
- When a session cannot continue (for example `Result.outcome = poisoned`), the task goes to `failed` with phase `irrecoverable`. A new task replaces it and names the old one in `supersedes`. The old session does not change.

### 5. Backlog storage

Everything arc stores for a repository is in `<repository>/.radian/arc/`.

```text
<repository>/.radian/arc/
  config.toml                     repository, gate profiles and commands, budgets, concurrency
  worker-brief.md                 the repository's standing worker instructions; every brief
                                  ends with them, and `init` writes a default once
  plans/<plan>.md                 plan fields and the request text
  tasks/<task>.md                 task fields (state, phase, after, limits) and the brief
  ledger/                         for each plan and task file: state_version and content hash;
                                  approvals; verdict sets
  runs/<task>/attempts/<attempt>/ execution.json, result.jsonl, attempt_finished.json, signal.json,
                                  stderr.log, verdicts
  runs/<task>/gate.json            the last background gate's outcome, for the next pass
  runs/<task>/gate.log             the output of the background gate process
  runs/<task>/auto_reverify.json   the (head_sha, remote main) pairs the loop reverified on
                                  its own, and the last max_auto_reverify stop
  runs/<task>/conflict_rework.json how many conflict reworks arc has written for the task in a
                                  row; the lead's rework and an attempt that does not conflict
                                  reset it
  attempts/<task>/<attempt>/      host-local attempt records (decision 7): start.json, identity.json,
                                  status.json, heartbeat.json
  attempts/<task>/state/          the command worker's own state directory, kept across the
                                  task's attempts (decision 7)
  gates/<stage>/                  the separate checkout for each gate stage; a review slot
                                  uses its own gates/review-<n>/ (decision 10)
  gates/review-<n>.lock           the lock of one review slot, <n> is 0 to concurrency - 1
                                  (decision 10)
  gates/<task>.gate.lock          the lock one task's running gate holds (decision 10)
  state.lock                      short lock for each state change
  runner.lock                     held for the life of one scheduling loop; its holder
                                  writes its pid there, which a viewer's header reads
  loop.log                        every line the scheduling loop prints, with an RFC 3339 UTC
                                  timestamp; a loop writes it, and the TUI reads it
  loop.log.1                      the previous loop.log, kept when loop.log reached 1 MiB
  worktrees/<task>/               the worker workspace for each task (decision 15)
```

- A task file keeps its path for its whole life. Its `state` (`todo`, `doing`, `review`, `done`, `failed`) and its `phase` are front-matter fields. Phases: `todo` has `ready`, `blocked`, `retry_wait`, `paused_budget`, `proposed`; `doing` has `starting`, `running`, `reconciling`; `review` has `verifying`, `rework_pending`, `awaiting_human`, `integrating`, `ready_to_merge`; `done` has `merged`; `failed` has `exhausted`, `cancelled`, `irrecoverable`.
- arc is the only writer. The lead changes plans and tasks only through the `radian arc mcp` tools. The owner's actions are the CLI's own library calls (`confirm`, `auto`, `pause`, `priority`, `start`, `merge`, `reject` and `reverify`): `radian arc` runs them, and the arc TUI calls the same functions in its own process once its merge page is built. The TUI's read-only pages change nothing.
- **Outside changes.** Each time arc writes a plan or task file, it records the file's `state_version` and content hash in the ledger. Before arc acts on a file, it compares the file with the ledger. When they differ, someone changed the file outside arc: arc does not act on that plan or task, and it shows it as changed outside arc until the owner resolves it. `radian arc adopt <id>` resolves it: arc records the current content as its own. `adopt` refuses (exit 3) when the outside change touched `state`, `phase`, an approval, or a verdict field. This finds mistakes and casual edits. It does not stop a lead that changes the ledger too (decision 11).
- arc reads `config.toml`, plans, tasks, and the ledger only in the main checkout, never in a worktree.
- Workers and gate stages do not read the backlog. A worker gets its brief as a copy on stdin. The wrapper adds every entry of `<repository>/.radian/arc/` except `worktrees/` to the worker's sandbox deny list, `worker-brief.md` included: the wrapper reads that file and puts its content in the brief on stdin. A file a brief points at under `runs/` reaches the worker as a copy in its worktree (decision 7), so the deny list stays as it is.
- Each state change is one transaction under `state.lock`: take the lock, check `state_version` and the hash, write a temporary file, fsync, rename on the same file system, fsync the parent directory, update the ledger the same way, release the lock. Git, ssh, and gate runs happen outside the lock.
- `runner.lock` allows one scheduling loop at a time. A second loop that cannot get the lock exits. The MCP server uses only `state.lock`, so the lead can add tasks while a loop runs.
- arc never commits a file in `.radian/arc/`. Whether git tracks `config.toml`, `plans/`, and `tasks/` is the owner's choice (decision 15).
- The fields frozen in v0 are identity, state and phase, attempt, and the verified sha. A field added after v0 is optional: it reads as its documented default when the file does not carry it, so a file an earlier build wrote stays readable and `schema_version` stays `1`. `schema_version` rises only when an existing field's meaning or shape changes. `followup_pending` (boolean, absent reads `false`) is such a field: it records that the task reached `done.merged` under the review follow-up rule (decision 10). `cost_unknown` (boolean, absent reads `false`) is another: it records that one of the task's attempts ended without reporting a cost, so the task's and its plans' cost sums are incomplete (decision 12). `flow` (string, absent reads `default`) is another: it names the `[flows.<name>]` section whose worker the task's attempts start and whose `gate_profile` gates it, and it changes only while `attempt` is `0`. `allow_noop` (boolean, absent reads its flow's `flows.<name>.allow_noop`) is another: an explicit `true` or `false` is the task's own, and an absent field takes the flow's value (decision 15), so a task can opt into or out of a no-op delivery without repeating what its flow already decides.
- `retry_at` is stored as an absolute UTC time.

### 6. States

| From | To | Condition |
|---|---|---|
| `todo.ready` | `doing.starting` | Every task in `after` is merged, a slot is free, and the owner started the task or the plan's auto level starts it. arc claims the task and creates an attempt in one transaction. |
| `todo.retry_wait` | `doing.starting` | The owner runs `radian arc start`: the task is claimed exactly as a `todo.ready` one, and `retry_at` is not consulted. The scheduling loop still waits for `retry_at` (decision 9). |
| `doing.running` | `review.verifying` | arc receives a valid attempt end record (token matches, result present) and the delivery check passes (decision 8). |
| `doing.running` | `todo.retry_wait` | The worker ended, and the failure is an infrastructure or model failure that can retry. |
| `doing.running` | `doing.reconciling` | arc cannot prove the state of the worker. arc does not start the task again. A person decides. |
| `doing.running` | `todo.paused_budget` | A task or plan budget is used up. Only `reset-budget` returns the task to `ready`. |
| `review.verifying` | `review.awaiting_human` | Each required stage passed for the same `verified_sha`. arc records `verdict_set_digest`. |
| `review.verifying` | `review.rework_pending` | A `commands`, `mutation` or `review` stage failed. arc sends the result to the lead. |
| `review.awaiting_human` | `review.integrating` | The owner merges (or the plan is at auto level `merge`) with the sha equal to `verified_sha` and the digest unchanged. |
| `review.integrating` | `review.ready_to_merge` | The integration stage passed against the current main as `base_sha`. |
| `review.ready_to_merge` | `done.merged` | Main is still `base_sha`, main fast-forwards to `candidate_sha`, the push to `origin` succeeds, and `origin/main` contains `head_sha`. |
| `review.awaiting_human` | `review.rework_pending` | The owner rejects the task with a note. |
| `todo.proposed` | `todo.ready` | The owner runs `radian arc confirm <task>`. The plan's `status` and `auto` do not change. |
| `todo.proposed` | `failed.cancelled` | The owner runs `radian arc cancel <task>`. |
| `failed.exhausted`, `failed.irrecoverable` | `failed.cancelled` | The owner runs `radian arc cancel <task>`: seen, given up. A stale gate record or lock is stopped first, by the same process check the `review` case makes. The attempt history, the verdicts and `total_cost_usd` stay. |
| `review.*` | `failed.cancelled` | The owner runs `radian arc cancel <task>`; a gate running for the task is signalled first (decision 9). |
| `review.*` | `todo.ready` | The lead adds a rework brief. The attempt number goes up by one. |
| `review.rework_pending`, `review.awaiting_human` | `review.verifying` | `radian arc reverify` (decision 11), or the scheduling loop's automatic reverify of a command failure once main moved (decisions 9 and 10): arc claims a new attempt without a worker. |
| any | `failed.*` | Retries or budget used up (`exhausted`), cancel (`cancelled`), or a session that cannot continue (`irrecoverable`). |

- A `todo.proposed` task is not a `todo.ready` task: the scheduling loop passes over it, `start` refuses it (exit 3, naming the phase), and a task whose `after` names it waits, because `after` waits for `done.merged`. `list` and `show` print it like every other phase.
- When the branch moves after the gate (`head_sha` changes), all verdicts and approvals for the old sha become invalid, and the task returns to `review.verifying`.
- When main moves after integration (it is no longer `base_sha`), the task returns to `review.integrating`.

### 7. The worker

For each attempt, the scheduling loop runs `radian arc work`. `radian arc work` is the trusted wrapper around the model. A person does not run it.

1. It creates or reuses the linked worktree `<repository>/.radian/arc/worktrees/<task>` on branch `work/<task>` (decision 15). The first attempt fetches the configured remote and main branch, starts from the remote main, and records `base_sha` in the host-local `attempts/<task>/base_sha`. At the end of each attempt the wrapper records the branch tip in `attempts/<task>/last_head`. A later attempt first checks that `work/<task>` still equals `last_head`; when it moved, the attempt fails before the worker runs. In single-host v0 all worktrees share one clone.

   After that check passes and before the worker starts, the wrapper runs the selected profile's `before_attempt` entries, in order, in the worktree (decision 10). An entry is the string `merge-main` or a table `{ run = "<command line>", timeout_secs = <integer> }`. A worktree this attempt created already starts from the fetched main, so `merge-main` does nothing then; a command entry runs before every attempt, the first included. `merge-main` fetches the remote main with the same explicit refspec the worktree setup uses, does nothing when `<remote>/<main>` is already an ancestor of `work/<task>`, and otherwise runs `git merge --no-ff --no-edit <remote>/<main>` in the worktree: the repository sets `merge.ff=only`, so `--no-ff` is required, and arc never rebases. The merge commit gets the identity the worker's commits get.

   A command entry runs `sh -c <run>` in the worktree with no sandbox, the same way a gate `commands` line runs, in its own process group; a timeout kills the whole group, and the time counts against the attempt's `max_wall_time_secs`. Its stdout and stderr go to one log file per command entry, `runs/<task>/attempts/<attempt id>/before/<n>.log`, where `n` is the entry's position in the list, from 1. It gets the wrapper's own environment plus `ARC_WORKTREE`, `ARC_TASK` and `ARC_ATTEMPT` with the values the command worker gets. Its output never reaches the worker's stdin: a worker that needs it reads the log or the files the command produced. A command that exits non-zero or runs past its timeout ends the attempt before the worker starts, as an infrastructure failure under the retry rules (no worker, no rework count); `attempt_finished.json` names the entry, its exit code or timeout and the log path, and `show` prints that reason. A `reverify` attempt runs no worker and no `before_attempt` command.

   A clean merge leaves the brief the worker receives unchanged; the merge commit is on the branch before the worker starts. A conflict leaves the worktree mid-merge (`MERGE_HEAD` present, conflict markers in the files) and puts a section at the top of the brief the worker receives on stdin: it names the merged `<remote>/<main>` and its short sha, lists the conflicted paths, and tells the worker to resolve them first, keeping both sides' intent, and commit the merge with `git commit --no-edit` before doing anything else. The brief stored in the task file does not change. A failed fetch, or a merge that fails for a reason other than a conflict, fails the attempt the way a failed worktree setup does, with git's message. The attempt's wall clock covers the fetch and the merge.
2. It runs the worker, in one of two ways.

   **The `radian exec` worker.** Unless the task's flow sets `command`, it runs the model:

   ```text
   radian exec -p - --session-id <session> --workspace <worktree> --profile workspace --yes --output jsonl
   ```

   The session is the attempt's (`[worker] rework_session`, decision 4): with `fresh` the wrapper passes `--session-id <task>-<attempt>` and never `--resume`; with `resume` the session id is the task id, and when that session's file exists in the worker's session directory the wrapper passes `--resume <task>` in place of `--session-id <task>` (the two flags exclude each other). With `resume` the wrapper decides from the file, not from the attempt number: an attempt that failed before the model started (a missing credential, a worktree that could not be prepared) leaves no session, and the next attempt starts it with `--session-id`. The wrapper records the session id it used in the attempt's `identity.json` and `execution.json`, and the claim recorded the session it decided on in `start.json` (decision 4). A reader takes the first of those records that names one, so `show`, the arc TUI and `attach` find a running worker's journal by its session id before the wrapper has written its end records, and an older attempt that has none falls back to the task id. The `workspace` tier is required: unattended work never runs in `full`.

   **The command worker.** When the task's flow sets `command` (decision 15), the wrapper runs that command instead: the array's first element is the program and the rest are its arguments, with no shell in between. The command runs with the task's worktree as its working directory; it receives the brief on stdin exactly as the `radian exec` worker would (a `merge-main` conflict section, a fresh attempt's hand-off, the task body, `worker-brief.md`); its stdout goes to `result.jsonl` and its stderr to `stderr.log`; it gets its own process group, the same signals, the same stall and wall-time limits, and after it exits the same git control-file check, delivery check (decision 8), push and records. A program that contains a `/` is a path, resolved from the repository root; any other name is looked up on `PATH`.

   The wrapper adds these variables to the command's environment:

   | Variable | Value |
   |---|---|
   | `ARC_WORKTREE` | The attempt's worktree, absolute. |
   | `ARC_TASK` | The task id. |
   | `ARC_ATTEMPT` | The attempt id, `<task>-<n>`. |
   | `ARC_SESSION` | The session id the claim chose, exactly as the `radian exec` worker gets it (decision 4). |
   | `ARC_SESSION_START` | `new` or `resume`: the value `session_start` picks for this attempt (a `resume`-mode later attempt whose session file exists picks `resume`, every other attempt `new`). Always set. |
   | `ARC_GIT_DIR` | `git rev-parse --absolute-git-dir` in the worktree. |
   | `ARC_GIT_COMMON_DIR` | The absolute common git directory. A linked worktree's objects and refs live there, so a sandboxed agent needs it writable to commit. |
   | `ARC_DENY_READ` | The paths the wrapper would give `--deny-read` to the `radian exec` worker, joined with `:`. |
   | `ARC_STATE_DIR` | An absolute host-local directory for the task, `<repository>/.radian/arc/attempts/<task>/state/`: outside the worktree, kept across the task's attempts, created by the wrapper. The command may keep its own state there, for example a session map. |

   The command's stdout is JSON lines, and the last line with `"type":"Result"` decides as it does for `radian exec`: `outcome` `completed` passes and any other value fails, and a stream with no `Result` line fails as `terminated`. `text` (a string) is the attempt's final report, which the hand-off section reads; `cost` is optional and has the shape `radian exec` writes (`micros`, `incomplete`, `estimated`). Without it the attempt's cost is unknown: it adds nothing to the task's or the plan's cost total, a budget never stops on it, and the cost is shown as unknown where costs are shown. A `cost` that is null, or that carries no `micros`, is a reported zero, the shape `radian exec` writes when it recorded no fee. When a claim starts a command worker for a task or plan that has a cost limit, `radian arc run`, `serve` and `start` print one line per attempt: `<task>: worker.command reports no cost; the cost limit does not apply`.

   A `fresh` attempt after the first also gets a hand-off section in front of the brief, under `## Where the previous attempt left off`: the newest earlier attempt's final report (the last assistant message of that attempt's `result.jsonl`, cut at 8,000 characters with a note when it is longer; a worker-less attempt, a `reverify`, writes none, so the section walks back to the newest attempt that did and names it), the commits of the task's own change (`git log --oneline <merge base of the remote main and the branch tip>..<branch tip>`) and its `git diff --stat`. It says that the full history is on the branch and that the worker should read the files rather than assume. The conflict section of a `merge-main` step stays first. A `resume` attempt's stdin is the brief alone.

   **Every brief ends with the repository's standing worker instructions.** When `<repository>/.radian/arc/worker-brief.md` exists and its content is not empty after trimming, the wrapper appends it as the last section of the brief the worker receives on stdin, after the conflict section, the hand-off and the task body. This holds for every worker: a first attempt, a rework (fresh or resume), and a follow-up task arc wrote. The wrapper reads the file when it composes that attempt's brief, so an edit takes effect at the next attempt and needs no restart. A missing file and one that is empty after trimming leave the brief exactly as it is without the file. A file larger than 32 KiB, a file that is not UTF-8, and a read error are not appended: the attempt goes on without the standing section, the attempt record carries one line `worker-brief.md skipped: <reason>`, and `radian arc show` prints it. Nothing about the worker's sandbox changes: the worker still cannot read `.radian/arc/`, and the content reaches it on stdin.

   **A file under `runs/` that a brief names reaches the worker as a copy.** When the wrapper composes an attempt's brief it finds every path in that text under `<repository>/.radian/arc/runs/` that names an existing file with the shape `runs/<task>/attempts/<attempt>/…`, copies the file to `<worktree>/.radian/arc-verdicts/<task>/<attempt>/<file name>` (creating the directories), and replaces the path in the text it sends with the worktree-relative `.radian/arc-verdicts/<task>/<attempt>/<file name>`. This covers the review rework's verdict line (decision 9) and a follow-up task's verdict paths (decision 10), and it acts on the composed text, so every brief kind and every task already written gets its copies. The task file is not changed: the lead and `show` still read the absolute path, and the original file stays where it is. A path that does not exist, is not a regular file, is larger than 1 MiB, or cannot be copied is left in the text as it is, and the attempt record carries one line `verdict copy skipped: <path>: <reason>`, printed by `radian arc show` the way the `worker-brief.md skipped:` line is; the attempt runs. The copy is a file in the worker's worktree: `.radian/` is ignored, so it is never committed and the clean-tree check does not see it, and a later attempt overwrites it.

   Before `start`, each `run` pass and `confirm` act, arc checks the worker line. Without a flow `command` it parses the line the worker would get — these fixed arguments, with placeholder values for the task, the worktree and the session, then the flow's `exec_args` — with the `radian exec` parser, in-process, without starting a session, calling a model or writing a file. A line the parser rejects, or that repeats an argument the wrapper owns (`--profile`, `--workspace`, `--session-id`, `--resume`, `--output`, `--yes`, `-p`), refuses the command with exit `3` and the parser's own message, names `flows.<name>.exec_args`, claims nothing and changes no file: `start` claims no attempt, `run` refuses before its first pass, `confirm` leaves the plan a draft. With a flow `command` set, the `exec_args` parse is skipped and arc checks instead that the program resolves: a program with a `/` must be an executable file and a bare name must be found on `PATH` as an executable file. A program that does not resolve refuses the command the same way, with a message that names `flows.<name>.command` and the program. Every flow's worker line is checked this way. When the parser cannot be reached in-process without a dependency cycle, the current executable runs it behind a hidden parse-only flag; that flag is an internal input and is not in the manual.

   **Before the first `before_attempt` entry runs, the wrapper records the repository's git control files.** They are `<common dir>/config`, `<git dir>/config.worktree` (the worktree's own git dir), `<common dir>/config.worktree`, every file under `<common dir>/hooks/` and `<common dir>/info/` except `<common dir>/info/refs`, and every `config` file and every file under `hooks/` in `<common dir>/modules/**` (submodules). `info/refs` is not a control file: any automatic `git gc` in the shared repository runs `git repack`, which rewrites it through `git update-server-info`, and only the dumb HTTP transport reads it, so a change to it says nothing about a worker's change to what the wrapper's git commands run. The wrapper finds the common dir and the git dir with the git calls it makes anyway. It holds the record in its own memory, never in the worktree and never in a file a worker can write. A file that is created, removed or changed counts as a change: the wrapper compares content, not the time. The wrapper compares the files once after the `before_attempt` entries and before the worker starts, so a command that changes one fails the attempt the same way a worker does, and again after the worker exits. This check does not depend on the worker's sandbox. It runs for every worker because a worker whose sandbox lets it write `.git/config` or a hook changes what every later git command of the wrapper, of a gate checkout, and of the scheduling loop runs. The wrapper's own worktree setup writes none of these files: it creates the branch with `--no-track`, and every fetch and push names its remote and refspec, so the shared config gains no branch section while another attempt runs. A control file larger than 1 MiB is not read whole: an attempt does not start while one of the recorded paths is that large, and one the worker creates is a change like any other. When the direct child exits, the wrapper stops everything the worker left in its process group (SIGTERM, then SIGKILL after the cancel grace) before it compares the files: a process the worker started cannot change a control file after the child's own exit, and nothing of the worker outlives the attempt.
3. After the worker exits, and before the wrapper runs any git command of its own, it compares the git control files with its record (decision 8). It then (not the worker) reads the `Result` and the exit code, reads `head_sha`, and lists uncommitted and untracked files. It pushes `work/<task>` only when `outcome` is `completed`, the git control files are unchanged, and the change is valid. After the push, it checks the remote ref with `ls-remote`. Every git command of the wrapper sets `core.hooksPath` to empty and `GIT_CONFIG_NOSYSTEM`, so no file the model can write changes what the wrapper runs.
4. Before the push, it checks that `work/<task>` exists, that `head_sha` descends from `base_sha`, that the worktree HEAD is on that branch, and that the tree is clean. If one check fails, the attempt fails, nothing is pushed, and the worktree stays for inspection.
5. Its last stdout line is its own `AttemptFinished` record: attempt id, token, exit code, outcome, `base_sha`, `head_sha`, dirty files, pushed, and remote sha. The radian `Result` is kept unchanged in `result.jsonl`.
6. When the wrapper sees the worker exit without a `Result` (crash, kill), the outcome is `terminated` and the attempt fails. Only when arc cannot reach the wrapper at all does the task go to `reconciling`.
7. It writes a host-local attempt record (token, pid and start time, session, worktree, branch, end result). After a restart, arc reads this record to reconcile. A flock on the worktree directory keeps two attempts of one task apart.
8. **It enforces the attempt's limits itself; the scheduling loop does not wait for it.** The limits are the task's `stall_timeout_secs` and `max_wall_time_secs` (else the `[limits]` values) and `[limits] cancel_grace_secs`; arc passes them when it starts the wrapper. A stall is no new line on the result stream for `stall_timeout_secs`, and `max_wall_time_secs` is an absolute limit on top. **The wall clock starts when the wrapper starts and bounds every step of the attempt**, the wrapper's own git commands included: a fetch, a push or an `ls-remote` still running at the deadline is killed with its process group, `signal.json` gets `wall_time`, and the wrapper still writes its records. Over a limit, or when a `cancel` records its signal, the wrapper sends SIGTERM to the worker's process group, waits the grace period, sends SIGKILL, writes `signal.json` with the failure class, and still writes its `AttemptFinished`. The limits live in the wrapper, so they hold after the `run` process that started it exits or is killed.

   **Every git call arc makes that talks to a remote is bounded**, wherever it runs: a `fetch`, a `push` or an `ls-remote` of the wrapper, the gate, the merge and `init` runs with the shorter of its own limit and `[limits] git_remote_timeout_secs` (integer, default `300`, `1` or more), and a limit that runs out kills the command's whole process group. A local git call (`diff`, `log`, `merge-base`, `status`, a local `merge`) has no limit of its own. A remote call that runs out is an ordinary failure of the step that made it, with the text `git <subcommand> timed out after <n> s`: a gate fetch fails the gate, a merge push leaves the task where a rejected push leaves it and the pass goes on, and `init` reports the line as a failed check. The key takes effect at the next git call.
9. It writes a heartbeat to `attempts/<task>/<attempt>/heartbeat.json` (the worker's pid, its process start time, and the last beat time) from a thread that runs from the moment the attempt directory exists until the wrapper has written its end record. It keeps beating while the wrapper sets up the worktree, waits on the model, and checks and pushes the result. The interval is about 15 seconds and at most a third of the attempt's stall window, so the window always holds at least three beats. The heartbeat is how a later pass decides whether an attempt is alive (decision 9); no `ps` call is needed for that.

The push credential is in the environment of the wrapper only. In v0 the wrapper and the model run as the same OS user, so this is not isolation.

### 8. Delivery check

`Result.outcome = completed` means that the run ended (ADR 0044). It does not mean that the task is done. arc checks delivery separately: a dirty tree, no valid change (unless the brief allows a no-op), a sha mismatch, or a change to any file under `.radian/arc/` fails the attempt. A task can never change the arc configuration, plans, tasks, or ledger through its branch.

The attempt also fails when the worker changed the repository's git control files (decision 7). The wrapper compares the files with its record before it runs any git command of its own after the worker. On a change it restores every recorded file to its recorded content and removes every file that was not there before, and the attempt fails with the reason `the worker changed git control files: <paths, comma-separated>`. A control file the wrapper cannot read back counts as a change: the record cannot prove it unchanged, so the restore puts the recorded content back. It does not push; the retry rules of decision 9 apply to the failure as they do to every other failed delivery check, and `AttemptFinished` and `show` carry the reason. A restore that itself fails leaves the attempt failed with both reasons, and the wrapper then runs no further git command for that attempt. The check does not depend on the worker's sandbox.

The change the delivery check counts is the attempt's own commits: the range from the tip the attempt started on to `head_sha`. A clean merge of main adds none, so a branch whose merge did not move it past that tip is still a no-op attempt, and the task's `allow_noop` decides: its own value when its file carries one, else its flow's `flows.<name>.allow_noop` (decision 15). The value is read at the claim of the attempt, so a `config.toml` change takes effect at the next attempt. The `.radian/arc/` check reads the task's own change against the main the attempt ran on (from the merge base of the remote main and `head_sha` to `head_sha`), so a merge commit never trips it, while a commit the worker made under `.radian/arc/` still fails. A merge commit on the branch never breaks the other checks: `head_sha` still descends from `base_sha`, and the tip the wrapper records in `last_head` is the tip the attempt ended on, so the next attempt's moved-ref check passes.

**Binary deliverables are ordinary git commits.** A flow whose work is images or other binary files commits them like any other file, and the delivery check is unchanged. Git LFS and reference-only deliverables (a commit that names an external path or hash instead of the bytes) are not supported; support waits until a repository needs it.

### 9. Failures, retries, stalls, and cancel

- Failure classes are infrastructure, model, verification, and cancel. Only infrastructure and model failures retry, with exponential backoff from 10 seconds to 5 minutes. The backoff exists for the scheduling loop: the owner's `start` claims a `todo.retry_wait` task at once as it claims a `todo.ready` one, while the loop releases the task only once `retry_at` has passed. A cancel does not retry. A verification failure goes to the lead for rework, except for a conflict with main when the profile runs `merge-main` before an attempt; arc writes no other brief. A worker attempt that ends on an unavailable model waits like the review stage does (the next bullet), and a model error of any other kind keeps these retry rules.
- **`max_attempts` counts retries, not attempts.** A task keeps `retry_count`, the number of retries arc has started since the task's last lead or review rework. A failed attempt retries while `retry_count` is below the task's `max_attempts` (else `[limits] max_attempts`) and raises it by one; when the count has reached the limit, the task goes to `failed.exhausted`. The attempt number is never compared with the limit. The lead's `add_rework` and the review rework set `retry_count` back to `0`; a conflict rework keeps it, so a worker that keeps failing still uses up `max_attempts` when conflicts keep returning the task to `todo.ready`. `attempt` still goes up by one for every attempt, and a `reverify` attempt is not a retry, so it changes neither `retry_count` nor the decision. The backoff follows the count: 10 seconds for the first retry, doubled for each later one.
- A `commands`, `mutation` or `review` stage, or the integration stage, that fails with reason `conflict` returns the task to `todo.ready` by itself when the selected profile's `before_attempt` contains `merge-main` (decision 10): the next attempt starts mid-merge, so arc writes that attempt's brief.
  - arc appends the brief to the task body and moves the task to `todo.ready` the way the lead's rework does (decision 6), with the heading `## Rework <n> (conflict with main)`. No new task state is added.
  - The text is fixed and short: the change conflicted with main at `<main short sha>` in `<stage>`; it lists the conflicted paths; the next attempt starts mid-merge; and it asks the worker to resolve the conflict keeping both sides' intent, commit the merge, rebuild, run the touched crates' tests, and change nothing else.
  - It never counts toward `max_attempts` by itself: a conflict rework is not a retry, but it keeps the task's `retry_count` instead of resetting it, so a worker that keeps failing behind repeated conflict reworks still reaches `max_attempts` and `failed.exhausted`. It does not count as an automatic rework either: it does not change `auto_rework` and never pauses the plan. The plan's `auto` level decides, as before, whether the next attempt is claimed by itself.
  - `[limits] max_conflict_rework` (default `3`, `0` or more) is how many conflict reworks arc writes in a row. While it has written fewer than the limit, a conflict writes the brief and the task goes to `todo.ready`; once it has written the limit, arc writes no brief and the task stays in `review.rework_pending`: `radian arc run` prints `<task> conflict with main -> review.rework_pending: <reason>` and `show` prints the same text as the `rework_reason`. `0` writes none, so the first conflict waits for the lead, and `1` writes exactly one. The lead's own `add_rework` is a person stepping in and sets the run back to `0`; so does an attempt that does not conflict (a verification that ends in anything else, and an attempt that never reaches the gate). arc's own review and conflict reworks do not reset it. The run and the retry count together bound the alternation of a conflict and a failing worker: a conflict rework keeps the retry count (the bullet above), so the failures between conflicts use up `max_attempts`.
  - A `reverify` attempt that fails on a conflict takes the same path.
  - Every other reason, and every conflict when the profile does not contain `merge-main`, keeps today's path to `review.rework_pending` and waits for the lead: the worker would not start mid-merge. The one exception is a `review` stage that failed with blocking items (the next bullet).
  - `radian arc run` prints `<task> conflict with main -> todo.ready (automatic rework)` for the transition.
- **A moved main re-runs the gate by itself when a command failed.** A scheduling pass reverifies a task the way `radian arc reverify` does (decision 10) when all of these hold: the task's plan has `auto` other than `off`; the task is in `review.rework_pending` because the `commands` stage or the integration stage failed with reason `command_failed` or `timeout`; and the remote main is no longer the main sha the failing verdict recorded.
  - Two guards stop a loop. The pass records each automatic reverify's `(head_sha, remote main)` in `runs/<task>/auto_reverify.json`, and a pair is reverified automatically at most once, so a main that does not move runs nothing again. `[limits] max_auto_reverify` (default `2`, `0` or more, `0` turns the feature off) counts the automatic reverifies of one task; when the count is used up, the task stays in `review.rework_pending`, `radian arc run` prints one line with the reason, and `show` prints the same text as the `rework_reason`. The plan is not paused.
  - A review stage failure other than `review_unavailable`, a conflict, a reject note, a delivery failure, and a task the lead returned to `todo.ready` are never reverified automatically by a moved main.
  - An automatic reverify starts no worker, is not a retry (it changes neither `retry_count` nor `max_attempts`), and does not count toward `auto_rework`. A reverify attempt that fails its gate does not count toward `auto_rework` either, whether the loop or the owner started it: `auto_rework` stays as it was, the task stays in `review.rework_pending`, and the plan is not paused by it. `radian arc run` prints one line for each: `<task> main moved (<short sha>) -> auto reverify`. The owner's `reverify` ignores both guards and does not use up the count.
- **A worker attempt that ends on an unavailable model waits and uses no retry.** A `radian exec` worker (a flow's `exec_args`; a command worker is unchanged, because it has no exec `Result`) whose failed attempt's last `Result` carries `model_error.kind` `unavailable` or `usage_limit` makes arc record that `model_error` object on the attempt, move the task to `todo.retry_wait` with a `retry_at`, and leave `retry_count` alone. The wait is the review wait's backoff: 5 minutes for the first model wait of the task, doubled for each further one in a row, capped at 60 minutes; when `model_error.retry_after_secs` is longer than that step it is used instead, still capped at 60 minutes. The next attempt that does not end in a model wait ends the run of waits. Every other failure keeps its class, backoff and count. The ordinary pass that releases a due `retry_at` moves the task back to `todo.ready`, and the task is claimed like any retry, but no retry is counted. `radian arc run` prints `<task> worker model unavailable -> retry at <UTC time>`; `radian arc show` prints the attempt's model error and the task's `retry_at`.
- **A used-up review session waits on its model and re-runs by itself.** A `review` stage whose session ended because its model was unavailable fails with reason `review_unavailable` (decision 10) and the task waits in `review.rework_pending` with its `retry_at` set. A scheduling pass reverifies such a task as `radian arc reverify` does (decision 10), on the same terms as a moved-main reverify: the task's plan has `auto` other than `off`; the claim starts no worker, is not a retry, is not an automatic rework, and does not pause the plan. It needs no moved main, does not use up `[limits] max_auto_reverify`, and has no count limit, because a model's usage window always resets. `radian arc run` prints `<task> review model unavailable -> retry at <UTC time>` when the stage fails and `<task> review retry_at passed -> auto reverify` when it starts the reverify. The owner's `reverify` may start it earlier, as for any failed verification stage. The wait is the task's `retry_at`: the failing session's `model_error.retry_after_secs` when it is present, at least 60 s and at most 6 h; otherwise 5 minutes for the first `review_unavailable` of a `verified_sha`, doubled for each further one in a row on the same `verified_sha`, at most 60 minutes. Any other review outcome ends the run of waits. The task's `rework_reason` is `review_unavailable: model <kind> (HTTP <status>), retry at <UTC time>`, with the parts that are null left out; arc writes no rework section, does not raise `auto_rework`, does not touch `retry_count`, and does not pause the plan.
- A `review` stage that failed with reason `review_blocking` returns the task to `todo.ready` with the next attempt's brief when the plan's `auto` is not `off`:
  - The heading is `## Rework <n> (review)`, numbered as the lead's rework is.
  - The text is fixed: one line saying the review found these items, to fix them and nothing else, to append commits and not to rebase; the blocking items, one per line, as `[level] path:line text`; and the line `Read the verdict for detail: <path>`, naming the attempt's review verdict. The path the worker reads is the copy in its worktree, `.radian/arc-verdicts/<task>/<attempt>/review.json` (decision 7); the task file keeps the absolute path.
  - It is an automatic rework: it raises `auto_rework`, and `max_auto_rework` pauses the plan and sets `auto` to `off` (decision 12); the task then stays in `review.rework_pending`.
  - With `auto` `off` the task stays in `review.rework_pending` and waits for the lead, as it does today.
  - `radian arc run` prints `<task> review blocking -> todo.ready (automatic rework)` for the transition.
- Defaults: `max_attempts` 3 retries, `stall_timeout` 15 minutes, `max_wall_time` 2 hours, `git_remote_timeout` 5 minutes, `max_cost` not set (no limit), `max_auto_reverify` 2, `max_gate_deaths` 2, `max_conflict_rework` 3, cancel grace period 10 seconds.
- A stall is no new line on the jsonl stream for `stall_timeout`. The wrapper sends SIGTERM to the worker's process group, waits `cancel_grace_secs`, then sends SIGKILL. `max_wall_time` is an absolute limit on top of it, counted from the wrapper's first step and applied to every git command the wrapper runs. `signal.json` records the failure class of whichever limit was hit; the attempt result takes its class from that record. `AttemptFinished` carries the outcome, the exit code and the failure text, not a class field.
- A cancel applies to one attempt: SIGTERM, a grace period, then SIGKILL. A command that waits for the attempt (`radian arc cancel`, `radian arc start`) takes the wrapper's `AttemptFinished`; a scheduling pass leaves it for the next pass. Without that confirmation the task goes to `reconciling`.
- `radian arc cancel <id>` takes a plan id or a task id, resolved as `reset-budget` resolves its id: an id that names both is refused (exit 3), and an id that names neither is an error (exit 1). Task form: a `todo`, `doing` or `review` task, and a task in `failed.exhausted` or `failed.irrecoverable`, ends at `failed.cancelled` — for a task that ran out of attempts or cannot continue, `cancel` is the owner saying "seen, given up"; `done.*` and `failed.cancelled` are refused (exit 3), with a message that lists the phases it accepts. A failed task has no process to signal; when a stale gate record or lock exists for it (its `runs/<task>/gate.json` record is `started` or `running`), cancel applies the same process check the `review` case makes and never signals blindly. A cancel leaves the task's attempt history, its verdicts and its `total_cost_usd` as they are. When a gate is running for a `review` task (its `runs/<task>/gate.json` record is `started` or `running`), cancel signals the gate process the way a stop does (decision 10) before the task moves. Plan form, in this order: the plan's `auto` becomes `off`; every task in `todo`, `doing`, `review`, `failed.exhausted` or `failed.irrecoverable` is cancelled by the task form's rules; `done.*` and `failed.cancelled` tasks are left alone; the plan's `status` becomes `cancelled`. A plan whose cancel ended every task it could act on has every task at `done.merged` or `failed.cancelled`, so it is finished when at least one task merged; a task file that changed outside arc is left as it is (decision 5). A task left at `doing.reconciling` does not stop the plan from being cancelled; the next scheduling pass ends it at `failed.cancelled`, after the same process check the task form makes. The command prints one `<task> <state>.<phase>` line per task it changed, then `<plan> cancelled`.
- A cancelled plan is never claimed, gated, merged or reported as waiting by the scheduling loop. The one transition a pass still makes for it is the `doing.reconciling` task the plan form's cancel left behind: the plan is final, so the pass ends that task at `failed.cancelled` rather than waiting for the owner.
- **A wrapper failure is recorded by the wrapper.** Every failure after the attempt directory exists writes the same `AttemptFinished` record a finished attempt writes (`runs/<task>/attempts/<task>-<n>/attempt_finished.json` and the host-local `attempts/<task>/<n>/status.json`) before the wrapper exits: a refused argument, a held worktree lock, a fetch that failed, a worktree that could not be prepared, a worker that could not start. The next pass applies that record at once and frees the attempt's `[limits] concurrency` slot; its class is the one its outcome and exit code give (an infrastructure failure unless the record says otherwise), and the retry rules above apply, so a retry is not counted as a rework. Only a failure before those directories exist (an invalid task name, a directory that cannot be created) leaves no record; reconcile then applies the attempt as an infrastructure failure once the heartbeat is older than the attempt's stall window (the last bullet).
- arc keeps no state in memory. After a restart it takes `runner.lock`, reads each attempt in `doing/` from its host-local record, and checks the token. Liveness comes from the wrapper's heartbeat: a last beat older than the attempt's stall window (its `stall_timeout_secs`, else `[limits] stall_timeout_secs`) means the wrapper is dead, and the retry rules apply. When both values are 0 the window is three beats, 45 seconds. A claim that has no heartbeat yet is judged by the age of its `start.json`. This path runs no `ps`: the `workspace` sandbox refuses it. `ps` is read only to compare a pid's start time before a signal is sent, so a reused pid is never signalled; when `ps` reports nothing (a sandboxed session) and a signal is due, the recorded pid alone is signalled.

### 10. Gate

- A gate is a fixed profile: a list of stages. A task's profile is its flow's `gate_profile` (decision 15), or `gate.profile` for a repository without `[flows]`: it gives the stages the gate runs and their `required`, the profile's `commands` and `key_commands`, and the acceptance rules. There are no conditions, no dynamic graph, and no override rules. A brief can add stages to the profile (`extra_stages`); it cannot remove a required stage. The `integration` stage is not part of a profile and runs for every task.
- **A scheduling pass starts a gate in the background and returns.** The gate is a separate `radian arc gate` process (an internal command, like `radian arc work`). It writes only its verdict files and its own run record (`runs/<task>/gate.json`); only a pass that holds `runner.lock` and `state.lock` moves the task's state, and it does so from what the gate left. A gate that a pass started keeps running after the pass, or the `run` process, exits.
- One gate runs per task at a time. The gate process holds `<repository>/.radian/arc/gates/<task>.gate.lock` from the moment it starts: the pass opens and locks the file and the child inherits the descriptor. A pass that finds the lock held starts nothing, so one sha never has two gates. A gate that dies releases the lock; the next pass starts it again, and a verdict already written for this attempt, stage and sha is reused, so the stages resume where they stopped.
- **A gate record has one of eight statuses**, in one list in the code that the parser and the manual's drift test both read: `started` (a pass wrote the record it started the gate with, and the digest of the inputs when it could plan them), `running` (the gate's own first write, with its pid and its process start time), `done`, `refused`, `error`, `no_record`, `died` and `interrupted`. A pass names the process it started in the `started` record too, once the process exists, so a stop that finds only that record still has something to signal.
- **A gate that exits without a record is not started again for the same inputs.** Before it starts a gate, a pass writes the digest of what the gate will read (`plan_verification`'s `inputs`, or for integration the equivalent digest of the task's shas, `config.toml` and the remote main) to `runs/<task>/gate.json` with status `started`; the gate's first act replaces that with `running`. A gate process that exits having written no record at all leaves the `started` one. When the `started` record carries that digest, the next pass records the fact as `no_record` for the same attempt with the inputs it started the gate with, in the same record and field a `refused` gate uses, reports it (`radian arc run` prints one line naming the task and saying that its gate exited without a record; `show` prints the same text as `rework_reason`), starts no gate for those inputs, and does not count the pass as changed. A change of inputs (a new head, a new main, a changed profile) allows one new start. A pass that could not plan the gate writes no digest; such a start is a death, not a `no_record` (the next bullet).
- **A gate arc stops itself is `interrupted`, and is restarted without counting.** A stop (SIGINT or SIGTERM on the scheduling loop) signals the gate it finds, waits `[limits] cancel_grace_secs` and kills it; once the gate process is gone the record becomes `interrupted`, keeping the attempt and the inputs it was started with. The next pass starts the gate again at once, reuses the verdicts already written, and counts no death. A gate whose record is still `started` is stopped too: a held gate lock means a gate process is there.
- **A start is counted exactly once.** The record behind a start is `running` (the gate's own first write) or the pass's `started` one. While the gate lock is held the gate may still be starting or running, and the pass starts nothing, as before. Once the lock is free the process is gone, and the pass has seen one death: it adds one to the record's `deaths` and starts the gate again. The one exception is a `started` record that carries a digest: that gate is `no_record` (the bullet above), not a death. When the count would pass `[limits] max_gate_deaths` (integer, default `2`, `0` or more) for the same attempt and the same inputs, the pass starts no gate and writes the record as `died` instead. A `died` record behaves exactly as a `no_record` one does: the summary reports it (`radian arc run` says the gate died after it started), `show` prints the same text as `rework_reason`, no gate starts while the inputs are unchanged, and the pass does not count as changed. A new `head_sha`, a new main or a changed `config.toml` allows one new start and begins again at 0 deaths. `0` stops at the first death, so the gate is started `1 + max_gate_deaths` times at most, whether or not the pass could plan it. The digest decides only whether a start's death is *carried* or *begins again*: with a digest on both sides, a different one begins the count again at 1; when either side has none (the gate could not be planned then, or cannot be planned now), there is nothing to compare, so the count carries forward. A `died` record written when the pass has no digest keeps no `inputs` field, so a later pass that can plan once more starts one new gate under the rule above. A start is never restarted for free.
- A gate records its outcome with the attempt it ran for: `done`, `refused` (a pre-stage check refused it: a moved branch, a stage this build does not run, a missing sha) or `error`. A pass reports a `refused` record and leaves the task in `review.verifying` with the reason recorded; it starts no new gate for that attempt until the attempt changes (`reverify` or `start` claims a new one) or the planning checks pass again (the branch came back, the profile changed). An `error` record is reported as an error, and the next pass starts the gate again. A stop reaches the stages the gate is running: the gate forwards SIGTERM to each stage's process group, waits for them, and exits without a record, so no build or session keeps writing in the checkout.
- `integration` runs the same way: a pass takes the approval and starts the integration stage in the background, and a later pass reads its verdict, checks main, and pushes. The stage locks still queue as before: one `commands` stage at a time, one checkout per stage, the remote Verify lock. A running gate takes no concurrency slot of either kind.
- **`commands` and `review` run at the same time.** When a profile lists both and neither has a verdict for this attempt and sha, the two stages start together: the review reads the task's diff and brief, not the commands' output, so it does not depend on the commands. Every other stage keeps its order (`mutation`, `ci`, then `human` and `integration` at merge). Both verdicts are written when each stage ends. A verdict that already exists for this attempt and stage is reused, so a gate that died while the pair ran resumes only the stage without a verdict.
  The round's outcome follows the profile order. A `commands` failure decides the round with the commands reason, even when the review passed or failed too: the review verdict is recorded (its cost counts and `show` lists its items), but arc writes no automatic review rework for that round. When `commands` passes and `review` fails, the review path below runs. The gate waits for both stages to end before it decides: a `commands` failure does not kill a running review, and a review failure does not kill a running `commands`; the review is bounded by `[gate.review] timeout_secs`. A stop signal reaches both running stages.
- The `review` stage does not queue behind the local `commands` lock. It is a read-only session that builds nothing, so it may run while another task's commands run.
- A verdict is never rewritten. Every verdict records `profile`, the name of the profile the stage ran under, so `show` can say which profile a task's gate ran. `radian arc reverify <task>` re-runs the gate for the same commit by claiming a new attempt without a worker (decision 11): the attempt number goes up, `attempt_id` and `token` are new, `head_sha` does not change, the attempt result's class is `reverify`, and nothing is pushed. The new attempt's verdicts are its own: an earlier attempt's verdict is not reused. The remote `work/<task>` must still equal `head_sha`; when it moved, the command exits 3 with the moved-branch reason and the task stays in `review.verifying`.
- A scheduling pass makes the same worker-less claim for a task a moved main unblocked (decision 9) and starts the gate in the background, so a later pass applies its verdict. The automatic claim does not check that the rework reason is a verification stage: the pass checked the reason itself, and the reason may be a failed integration stage. Everything else is the owner command's: the new attempt's number, `attempt_id` and `token`, the class `reverify`, the unchanged `head_sha`, and no push.
- Stages are `commands`, `mutation`, `review`, `ci`, `human`, and `integration`. Each stage runs once against the verification candidate and writes one verdict.
- **An empty change passes the gate.** A task's own change is empty when the diff from the merge base of the remote main and `verified_sha` to `verified_sha` names no path; a commit that adds no content on top of main counts as empty. Such a task still runs the profile like any task (decision 8). `commands` runs the profile's commands on the candidate, which is the remote main when main did not move: nothing about the empty change fails it. `mutation` has nothing to mutate and passes; this build does not run it, so a profile that lists it is still refused as unbuilt, for that reason and not for the empty change. `review` passes without starting a session: its verdict is a pass whose `review` report holds a summary saying that the task's change is empty and empty `blocking`, `suggestions` and `verified`, with no session id and no cost. `human` is the owner's approval and does not change: it still binds to `verified_sha` and the verdict set digest. `integration` merges the empty change onto the current main (the candidate is the remote main when main moved) and runs the key commands on it as usual.
- Before the verification stages run, arc fetches `[repository] remote` and builds the verification candidate in the stage's checkout. When the remote main is an ancestor of `verified_sha`, the candidate is `verified_sha` itself. Otherwise the candidate is a merge commit of `verified_sha` onto the remote main, made in that checkout and never pushed; the merge uses arc's own commit identity, so the same inputs build the same tree. A merge conflict is a failed stage: its reason is `conflict`, its verdict lists the conflicted paths, and the task goes to `review.rework_pending` or, when the profile's `before_attempt` contains `merge-main`, to `todo.ready` with the rework arc writes (decision 9). `verified_sha` stays the task's commit: the approval, the digest and the merge bind to it, and the candidate is evidence, not a new identity. A verification stage's verdict records `sha` (`verified_sha`), `main_sha` (the remote main the candidate was built on) and `candidate_sha` (the commit the stage ran on).
- **arc's own fetches into one repository take turns.** Before every `git fetch` it runs, arc holds an exclusive `flock` on `<git common dir>/radian-arc-fetch.lock`, resolved with `git rev-parse --git-common-dir` so every worktree of one repository shares it, and releases it when the fetch ends. Waiting for the lock counts against the same `[limits] git_remote_timeout_secs` limit the fetch already has, and a wait that runs out fails the stage with a reason that names the lock. A fetch arc did not start, a person's own `git fetch` included, is not serialized by it.
- `commands` runs only the fixed commands of the profile on a separate checkout of the candidate. A brief cannot add a shell command.
- `commands` and `mutation` are exclusive: one at a time, in separate trees, with no shared build state.
- `review` is a read-only radian session. It is not the worker session.
  For each verification it runs one `radian exec` in its own checkout of the verification candidate, with the candidate as the workspace and `--tools read,grep,glob`: no shell tool, no write tool, and no MCP tool is mounted. Its model route is `[gate.review] exec_args` (default: `[worker] exec_args`), and `[gate.review] timeout_secs` is its wall-time limit (default 900).
  Up to `[gate.review] concurrency` review sessions run at once in the repository (integer, default `2`, `1` or more); `1` is one at a time. A session holds one review slot: the lock `gates/review-<n>.lock` and the checkout `gates/review-<n>/` of that slot, so no two sessions share a checkout. One task never runs two reviews at once; its gate lock sees to that.
  A task's **first review** is a review stage run when no earlier attempt of the task has a `review` verdict. It reads `[gate.review.first] exec_args` and `[gate.review.first] timeout_secs` when they are set; an unset key falls back to the `[gate.review]` key and, for `exec_args`, then to `[worker] exec_args`. A rework review never reads `[gate.review.first]`. Both keys are read when the stage starts, so a change takes effect at the next review.
  The prompt is built in: the task's brief, the commit list and the diff from `git merge-base <main sha> <verified_sha>` to `verified_sha` (the task's own change, not main's), and the instruction to check the change against the brief and the repository's rules (`AGENTS.md` and the ADRs the brief names). A rework round's prompt is different (below).
  `[gate.review] prompt_file` is appended to it.
  The session ends with one fenced `json` block, and arc parses the last such block: `{"summary": string, "blocking": [item], "suggestions": [item], "verified": [string]}`. An item is `{"level": "critical"|"major"|"minor", "file": string, "line": integer, "text": string, "pre_existing": true}`. `text` is required; `level`, `file`, `line` and `pre_existing` may be absent. A plain string is an item with only its `text`, so a verdict written before the object form still reads.
  `summary` is 2 to 6 sentences on what the change does.
  An empty `blocking` passes the stage; a blocking item fails it with reason `review_blocking`, and the rework reason lists the items, each as `[level] path:line text` with the parts the item does not have left out. An item whose `text` starts with a tag that repeats its own level (`[major]`, any case, spaces allowed) prints that level once: the leading tag is dropped from the text, and a `text` that starts with another tag keeps it. The verdict on disk is never rewritten.
  `suggestions` and `verified` never fail the stage.
  No parsable block, a missing field, a value outside a closed set, a timeout, or a session error runs the session once more; when the second run is unusable too the stage fails with reason `review_output` (or `review_timeout` when the last run timed out), and the verdict records both session ids. A session whose `Result` carries a `model_error.kind` of `unavailable` or `usage_limit` is **model unavailable**: the stage does not run it a second time, it fails at once with reason `review_unavailable`, and its verdict records the session id and that `model_error` object as read. Its cost counts toward the budget as any review's does, and the wait and automatic reverify rules are decision 9's.
  The verdict records the four fields, the session ids, their cost and the settings the session ran with (`review_settings`: `round`, `first` or `rework`; the `exec_args` source key; `timeout_secs` and its source key) beside the usual `sha`, `main_sha` and `candidate_sha`; a rework round also records how many blocking items it moved to `suggestions` as `review_pre_existing`. The recorded cost counts toward the task's budget (decision 12).
  A review run of an attempt never reuses a session id whose journal already exists: when `<attempt id>-review-<run>` is in the session directory, the stage uses `<attempt id>-review-<run>-<k>` with the smallest free `k`, and writes its logs under the matching `review-<run>-<k>` name. The verdict's `review_session_ids` lists the ids the stage actually used, so `show` and the arc TUI find every run.
  `review` runs at the same time as `commands` and before `human`; a profile that lists both must list `commands` first, because the round's outcome follows that order (above).
  Its verdict is bound to `verified_sha` and is part of `verdict_set_digest`, and `radian arc reverify` runs it again.
- **A rework round.** A review is a rework round when an earlier attempt of the same task has a `review` verdict with a `sha` other than the commit under review; the newest such verdict is the previous review. A review of the same commit as the previous review (a `reverify` of an unchanged head) gets the first review's prompt, with nothing treated as pre-existing, but it reads the `[gate.review]` settings because an earlier review verdict exists. The first review of a task is unchanged.
  A rework round's prompt holds the brief, the previous review's blocking items, the commit list `<previous sha>..<sha>`, and the increment instead of the full diff. It asks the session to check that each previous blocking item is fixed, to review the increment, and to list every problem it finds. The full diff is not in the prompt; the session can read the files. A previous sha that is not a commit in the checkout makes the review a first review, so nothing is treated as pre-existing.
- **The increment.** The reviewed lines are the new-side lines of `git diff <previous sha> <sha>` that are also new-side lines of the task's own diff. A line that came in only with a merge of main is not in the task's own diff, so it drops out. The increment diff is the task's own diff restricted to the hunks that hold an increment line.
- **`pre_existing`.** After a rework round's report is parsed, arc moves a blocking item to `suggestions` and marks it `"pre_existing": true` unless (a) its `file:line` is within 3 lines of a line the task's own change added or changed in the same file, (b) it is in the same file as, and within 10 lines of, a blocking item of the previous review, so an unfixed earlier item stays blocking, (c) its `level` is `critical`, or (d) it has no `file` or no `line`. The task's own change is the new side of `git diff <the merge base of the remote main and the head>..<head>`, the same diff the first review reads: the rework's increment decides only what the rework prompt shows, not this rule. An item in a file the task's own change does not touch, or more than 3 lines from any line it changed in that file, is demoted. A `critical` item blocks in every round, wherever it is: the position of a line does not prove that a problem is harmless or old. An item without a place stays in `blocking` at its level, because a missing `file` or `line` is the session's omission, not evidence that the problem is old. A moved item keeps its `level` (`major` included), so the follow-up task carries it at that level; `minor` items keep the window rules. This is arc's check, not the model's: whether a line changed is not a matter of opinion. The stage passes when no blocking item is left, and the verdict records how many items arc moved as `review_pre_existing`.
- **The review's follow-up task.** A task is **open** when it is in `todo.ready`, `doing.*` or `review.*`; a task in `todo.proposed`, `done.*` or `failed.*` is not open. When a plan has no open task, arc collects the suggestions of its merged tasks and proposes one follow-up task for the plan, and no more. At the moment a task reaches `done.merged`, on every merge path, arc records `followup_pending` on the task when `[gate.review] propose_followups` is `true` and the task is not itself a follow-up. A merged task of the plan is collected when it is `done.merged`, carries `followup_pending`, is not itself a follow-up, and no earlier follow-up of the plan names it in its `after`: a follow-up's `after` is the merged tasks it collected, so a task is collected at most once, and a collected task whose follow-up is later cancelled stays collected. A task without the field — merged before the field existed, or merged while `propose_followups` was `false` — is never collected, whatever its review verdicts say; an old per-task follow-up therefore collects nothing and is never collected itself. For each collected task arc reads every `review` verdict of the task, oldest attempt first, and collects every `suggestions` item of every round; the items arc moved as `pre_existing` are in `suggestions`. Every round is read, not only the newest: a round that failed can carry a demoted item, and a later round can pass with nothing to suggest. Nothing from `blocking` is collected: a merged task's blocking items were fixed or the review would not have passed, so a round that only had blocking items contributes nothing. Two items are the same when their `file`, `line` and `text` are equal after a leading tag that repeats the item's own level is removed and whitespace is collapsed; the newest copy is kept, and an item with the same `file:line` and other text is kept as its own item. That duplicate rule holds within one merged task; items of different tasks are never merged. When at least one item is left and `[gate.review] propose_followups` is `true` (the default), arc adds one task to the plan, and no more:
  - id: the next id in the task sequence;
  - slug: `<plan slug>-followups`, cut to the 48-character slug limit with a trailing `-` removed; when the plan already holds a task with that slug, `-2`, `-3`, … is appended within the limit;
  - title: `Follow-ups from <plan id>'s reviews`;
  - `after`: the collected merged tasks, in merge order;
  - phase: `todo.proposed`, so it waits for the owner's `confirm`;
  - `allow_noop`: `true`, because its brief lets each item be left with a one-line reason, so an attempt that adds no commit may deliver nothing.

  Its brief is fixed: one line saying that the items are from the reviews of the plan's merged tasks and that each item is to be fixed or left with a one-line reason in the final answer; then one section per collected task, headed `From <task id>`, holding that task's items grouped by the round they came from, each group headed `From review <n> (attempt <n>):`, one item per line as `[level] path:line text`; then the path of every review verdict. Each path the worker reads is its copy in the new task's worktree, `.radian/arc-verdicts/<task>/<attempt>/<file name>` (decision 7), including a verdict of a merged task; the new task's file keeps the absolute paths. An item whose `text` starts with a tag that repeats its own level prints the level once, as in the rework reason above. A plan whose merged tasks left no item gets no follow-up. A follow-up task is never collected: arc recognises one by a shape it gave it — the per-plan shape (the title `Follow-ups from <plan id>'s reviews`, the `<plan slug>-followups` id, `allow_noop`, a non-empty `after` list, and the fixed first line of its brief), or the per-task shape an earlier arc wrote (the title `Follow-ups from <task id>'s review` with that task as its only `after` entry) — and skips a merged task that has it, so its unfixed items stay in its verdict and in the task's final report. An ordinary task that carries only the title is collected like any other task, and its `after` collects nothing. With `propose_followups` `false` arc adds none; the lead's MCP `add_task` on a confirmed plan is not affected by the switch. arc checks after every change that can leave a plan with no open task: a merge, a `cancel`, and every scheduling pass. The check and the write are one transaction under `state.lock`: under that lock arc re-checks that the plan is not cancelled and has no open task, and which merged tasks it collects, so an owner's `confirm` between a pass's read and its write cannot add a follow-up to a plan that now has an open task. The check is idempotent: a second run adds no task. A plan whose file changed outside arc is not acted on; the merge that triggered the check stands, with a warning line, and the scheduling pass reports it in its summary. `radian arc run` prints `<new task id> proposed (follow-ups from <plan id>)`.
- `integration` merges `head_sha` onto the current main in a temporary tree and runs the key commands of the profile on the result. It records `base_sha` and `candidate_sha`. When main is still the task's `base_sha`, `candidate_sha` is `head_sha`. Otherwise it is a merge commit of `head_sha` onto main. arc never rebases a task branch, because a rebase changes the sha that the gate verified.
- Each stage runs in its own checkout under `<repository>/.radian/arc/gates/<stage>/`.
- A profile has `before_attempt` (array, default `["merge-main"]`): the steps the wrapper runs in the task's worktree before the worker starts (decision 7). An entry is the string `merge-main` or a table `{ run = "<command line>", timeout_secs = <integer> }`: `run` is required and not empty, `timeout_secs` is optional, `0` or more, and defaults to `gate.command_timeout_secs` (`0` means no limit), and any other key is a config error. The entries run in the order listed: `merge-main` does nothing on a first attempt, and a command runs before every attempt, the first included. Any other string is a config error, and `[]` runs nothing. The wrapper uses the task's profile (its flow's `gate_profile`, else `gate.profile`), and a change takes effect at the next attempt. A profile the file no longer defines fails the gate's planning with the missing-profile message, now naming the task's flow and its `gate_profile`; the wrapper fails an attempt that must run a step with the same message.
- The default profile is `commands` (required), then `human` (required). The radian repository profile is `commands` (required), `mutation`, `review`, then `human` (required).

### 11. Approval

- The MCP tools for the lead are `add_plan`, `add_task`, `update_task`, `update_plan`, `add_rework`, `list`, and `show`. There is no MCP tool to confirm, start, merge, reject, reverify, change the auto level, approve, or reply to the channel below.
- **The channel to the lead.** `radian arc mcp --claude-experimental` (boolean, default off) makes the server push task and plan transitions to an MCP client that carries Claude Code's channel extension. With the flag, the `initialize` answer declares `capabilities.experimental["claude/channel"] = {}` and does not declare `claude/channel/permission`: the server never relays permission prompts. The supported protocol versions are the known versions up to and including `2025-11-25`; a `server/discover` request is therefore answered with the unsupported-protocol-version error, and an `initialize` that asks for `2026-07-28` is answered with `2025-11-25`. The server's `instructions` text gains one paragraph: events arrive as `<channel>` blocks with the meta attributes below, they are one-way (there is no reply tool), and the lead reads the details with `show`.
- **The channel reads the store by polling.** After the handshake the server reads every plan and its tasks once (the baseline; nothing is sent for it), then again every 5 seconds, with the read-only store call the CLI's `list` uses. It takes no lock. A read that fails (a file changed outside arc, a parse error, a lock it cannot get) sends nothing that round and tries again next round; it never ends the server and prints nothing.
- **Which task transitions are sent.** One event per task whose `state.phase` differs from the previous read and whose new value is one of `todo.proposed`, `review.awaiting_human`, `review.rework_pending`, `done.merged`, or any phase of `failed` (`failed.exhausted`, `failed.cancelled`, `failed.irrecoverable`). A move into `todo.ready` sends one too, from one of two previous phases: `todo.proposed` (the owner's `confirm <task>`) and any `review.*` phase (the lead's `add_rework`). The owner's reject does not move the task into `todo.ready`: it keeps it in `review.rework_pending` (decision 6), so its event is the `review.rework_pending` one above and its second line is the note. A rework arc writes itself (a conflict with main, or a review that failed with blocking items) is not an owner action: the poller tells it apart by the suffix its rework heading carries and sends nothing for it. A task that is new since the previous read counts as a transition from nothing. Every other change (`doing.*`, `review.verifying`, `review.integrating`, a `todo.retry_wait` or `todo.paused_budget` task that became `todo.ready`, a title edit) sends nothing: each event costs the lead a model turn. The phases and the previous phases are each one closed list in the code that the manual's drift test reads.
- **Which plan transitions are sent.** One event per plan field whose value differs from the previous read, over the closed set `status` and `paused`, and only once the plan has been read before: a plan that is new since the previous read sends nothing for either field, so a plan that appears already confirmed is silent. `status` is sent only for `draft` to `confirmed`; a plan that returns to `draft` with a change record, or that is cancelled, sends nothing. `paused` is `true` when the plan is `confirmed` and its `auto` is `off`; a `draft` plan is not paused, it waits for the owner's confirm. A read that changes the plan's `status` sends no `paused` event: `update_plan`'s change record returns a confirmed plan to `draft` and sets `auto` to `off` in the same write, and a confirm takes a draft plan to `confirmed`, and neither is a pause. On a plan whose `status` did not change, the event is sent in both directions: `radian arc pause` and the automatic rework limit's `auto` `off` send the pause, and the next `auto` level that is not `off` sends the resume. `auto` is the only field `list --json` exposes for this, so a change of level that stays `off` or never leaves it sends nothing, and neither does a change of `priority` or a title. A cancelled plan is final (decision 3) and sends no plan event at all. `status` and `paused` are one closed list in the code that the manual's drift test reads.
- **The notification.** The method is `notifications/claude/channel`. A task event's `content` is one line `<task id> <previous state.phase or "new"> -> <state.phase>`, then, when the task has a `rework_reason` (the same text `show --json` gives), a second line with it. Its `meta` has exactly these keys, every value a string: `task` (the task id), `plan` (the plan id), `state`, `phase`, and `previous` (the previous `state.phase`, or `new`). A plan event's `content` is one line `<plan id> <field> <previous> -> <value>`, then, when the pause is the automatic rework limit's, a second line with the reason that limit recorded beside the task. The record stays on the task's attempt after the owner resumes, so only a record that belongs to this pause is its reason: a record an earlier read found while the plan was paused is not, and the owner's own `radian arc pause` sends no second line. A record a read finds while the plan is not paused is the reason of the pause that follows only while it is still `pending` (decision 12): the automatic rework limit writes the record before it sets `auto` to `off` and clears the marker after, so a read between those two writes, the poller's baseline read included, does not take it from the pause the next read reports. An applied record a running plan still shows belongs to a pause an earlier read saw, or to one that ended before the poller connected, so the owner's next pause does not repeat it. Its `meta` has exactly these keys, every value a string: `plan` (the plan id), `field` (`status` or `paused`), `previous` and `value` (the status text or `false`/`true` for `paused`), and no `task` key, so a reader tells a plan event from a task event. A meta key stays letters and underscores: Claude Code drops a key with any other character. The poller stops when the client closes the connection.
- The channel is the stdio connection to the lead's own process: no network and no new telemetry (ADR 0013). It carries no owner action and makes no write.
- `update_task` changes a task in `todo` (any phase) of a plan that is not `cancelled`: its `title`, its original brief, its `after` list, `allow_noop`, or `extra_stages`, and the call gives at least one of them. The phase does not change: a `todo.ready` task stays ready and a `todo.proposed` task stays proposed, so a change to `after` that makes the task wait on a task not merged yet is allowed, because the scheduler already waits on `after`. The `title`, `after` and `extra_stages` rules are `add_task`'s, through the same check: a title that is empty is a usage error, each `after` id names a task of the same plan or a `done` task, a task never waits on itself, and an `after` cycle is refused. `brief` replaces only the original brief, the text before the first `## Rework <n>` section; every `## Rework <n>` section and the change records below it are kept in order. Every successful call appends one line to a `## Changes` section at the end of the task file, created on first use: `- <RFC 3339 UTC> update_task: <the fields that changed, comma-separated>`. Every other state is refused with the state in the message, and a task in `review.*` is refused with a line that names `add_rework`. The write is one transaction under `state.lock`, and the file it leaves matches its ledger.
- The TUI's owner actions are the CLI's library calls, not a subprocess: `confirm`, `auto`, `pause`, `start`, `merge`, `reject`, `reverify`, `cancel` and `priority` run in the TUI process. Merge, reject, changing the auto level to `merge`, and `cancel` ask for confirmation first, and a reject takes a note and refuses an empty one. An action that cannot take `state.lock` shows the CLI's message and changes nothing. `start` does in the TUI what `radian arc start` does; the TUI holds no `runner.lock` (decision 13), and the `radian arc serve` loop it starts when none runs advances the rest.
- On the plans page, `c` confirms a draft plan when the plan column has the focus and a `todo.proposed` task when the task column has it; `x` cancels the selected task, or the selected plan and the tasks its cancel will end, after a `y/n` float; it acts only on a task `cancel` accepts (decision 9), so a `done` or `failed.cancelled` task gets no float; and `+`/`-` move the selected plan's priority one step toward `P0`/`P5`. A refused action shows the CLI's message in the footer and changes nothing. The left plan list and the selected plan's frame label draw the plan's `P<n>` in the one `priority_p0`..`priority_p5` theme role of that priority (ADR 0029).
- The plan list's mark is one of seven, the first rule that holds: `✕` a cancelled plan, by its `status` or by all its tasks being `failed.cancelled` (the rest of its row is weak), `◌` a `draft` plan, `◉` a task is `review.awaiting_human` or `todo.proposed`, or no task is open and a task is `failed.*` other than `failed.cancelled`, `●` a task is `doing.*` or in a `review.*` phase other than `awaiting_human`, `◍` `auto` is `off` and a task is open, `○` a task is open, and `✓` every task is `done.*` or `failed.cancelled` with at least one `done`. A plan no rule matches draws `○`. Each mark has its own theme role (`plan_needs_you`, `plan_running`, `plan_queued`, `plan_paused`, `plan_done`, `plan_draft`, `plan_cancelled`; ADR 0029). A task row draws its own mark: `✓` `done.merged`, `×` `failed.cancelled`, `●` `doing.*` and a `review.*` phase other than `awaiting_human` and `rework_pending`, `!` `review.awaiting_human`, `review.rework_pending`, `todo.proposed`, `failed.exhausted` and `failed.irrecoverable`, and `◻` every other `todo.*` phase; the mark and the `state.phase` text take the mark's theme role (ADR 0035). One predicate, `task_needs_owner`, is the owner's set — `review.awaiting_human`, `todo.proposed`, `failed.exhausted` and `failed.irrecoverable` — and both the plan's `◉` rule and the task mark read it, so the row that made a plan `◉` is a `!` row; `review.rework_pending` draws `!` for the lead without being in that set, and `failed.cancelled` stays `×`. A board card draws `!` in the `needs you` column, which is the wider "who acts next" question and also holds `todo.paused_budget` and the tasks of a paused plan, and the task mark elsewhere; the board's finished list draws the task mark, so a `failed.exhausted` or `failed.irrecoverable` row carries `!` and a `failed.cancelled` row `×`. The summary row is three columns — the auto level, `merged/total` and the cost — each padded to the widest value the view lists, the count and the cost right-aligned, and no status prefix. `total` counts the plan's tasks that are not `failed.cancelled`: a cancelled task is not work left to do, so a plan with one merged and one cancelled task reads `1/1`, and a plan whose tasks are all cancelled reads `0/0`. The task list's `state.phase`, `#n`, cost and trailing text start at the same column on every row, flat or graph: the id block (`connector + mark + id`, plus the one space before the phase) has one width per plan and a deep row's id is cut with `…`, and the space before the phase is always kept (a narrow page cuts the id one cell earlier to hold it), and the cost column is the widest cost, right-aligned. The `◉` an exhausted or an irrecoverable task draws is the owner's to clear with `radian arc cancel <task>` (decision 9), which moves the task to `failed.cancelled`. **A task row shows the task's flow in its own column** between the id block and `state.phase` when the repository defines a flow other than `default`, the same rule `radian arc list`'s flow column uses: the column is one width per plan, every row draws its flow (`default` for a task with no `flow` field), and a repository whose `config.toml` has no flow besides `default` draws no flow column and renders exactly as it did before flows existed. A `todo.ready` task a full limit holds ends its row with the queue reason `radian arc show` prints (`waiting for a free <flow> slot`, else `waiting for a free concurrency slot`), read from the same function rather than re-worded in the TUI. **The task page's frame label always names the task's flow** (`flow <name>`, `default` when its file has none) with the task's other fields. **When the repository defines more than one flow, the board's `DOING` heading adds each flow that has running tasks as `<name> <running>/<concurrency>` after the total** (`DOING 2 · code 1/1 · image 1/1`); the counts are the repository's `doing` tasks, the ones the queue reasons read, and a repository with one flow keeps the plain total.
- `confirm <id>` takes a task id as well as a plan id. A draft plan becomes `confirmed`; a plan that is already `confirmed` or `cancelled` is refused, and so is a task whose plan is `cancelled` (exit 3). A `todo.proposed` task becomes `todo.ready`, and the plan keeps its `status` and `auto`; a task in any other state is refused (exit 3). An id that names both a plan and a task is refused as every command refuses it.
- `reject <task> --note <text>` records the note in the task's run directory and moves the task to `review.rework_pending`. Without `--claude-experimental` arc sends nothing: the lead reads the note with the MCP `list` and `show` tools. With the flag the move is one of the sent transitions, and the event's second content line carries the note as the task's `rework_reason`.
- `reverify <task>` is an owner command; there is no MCP tool for it. It applies to a task in `review.rework_pending` or `review.awaiting_human` whose `rework_reason`, if any, is one a re-run can fix: a failed verification stage (`commands`, `mutation`, `review` or `ci`, with any reason), or the integration stage failed with reason `command_failed` or `timeout`, the same stage and reason pair the automatic reverify of a moved main accepts (decision 9), with no main move needed. A reject note, a delivery failure, an integration failure with any other reason, and any other state are refused (exit 3). It also applies to a task in `review.verifying` whose gate is stuck: its `runs/<task>/gate.json` record names the task's current attempt with status `no_record` or `died`, and no gate process holds the task's gate lock. Any other `review.verifying` task is refused (exit 3). It claims a new attempt without a worker (decision 10), moves the task to `review.verifying` and verifies it at once, as `start` does after a pushed attempt. A reverify attempt is not a retry: it changes neither `retry_count` nor `max_attempts`, costs no worker, and is not an automatic rework; a failed reverify does not count toward `auto_rework` either. A `review` stage it runs still counts toward the budget (decision 12).
- A merge binds to `verified_sha` and `verdict_set_digest`. A new review of the same sha changes the digest and makes an older approval invalid.
- In v0 this is a process rule, not a security boundary: the lead and arc run as the same OS user, and the arc files are in the repository where the lead works. The lead can run the CLI from a shell or change the files. A real authorization boundary needs a separate identity and a separate store for arc. This ADR does not claim one.

### 12. Auto levels

`auto` is a plan field. Only a confirmed plan can have `auto` other than `off`. A cancelled plan keeps `auto` `off`.

| Level | What arc does | Where it stops |
|---|---|---|
| `off` | Nothing by itself. The owner starts and merges each task. | Each step |
| `run` | Starts each task when its `after` tasks are merged, and runs the gate. | `review.awaiting_human` |
| `merge` | `run`, and merges when every required stage and integration passed. | Failure, budget, or conflict |

- A failed gate sends the task, the verdicts, and the diff to the lead, except a review that failed with blocking items when the plan's `auto` is not `off`: arc writes that rework itself (decision 9). When the lead adds a rework brief, arc starts the next attempt.
- `max_auto_rework` (default 2) limits automatic rework for one task: a review rework counts, a conflict rework does not. A failed reverify does not count either, whether the loop or the owner started it. When a task reaches it, arc pauses the whole plan and sets `auto` to `off`. It writes the reason beside the task's attempt as `paused.json` before that plan write, marked `pending` until the write is done, so a reader between the two knows the pause is still to come.
- A plan budget (`max_cost`, `max_wall_time`) adds to the task budgets. When a plan budget is used up, arc pauses the whole plan, and its running tasks go to `todo.paused_budget`.
- Cost is counted per attempt. `Result.cost` is the session total (ADR 0044), so arc counts the cost that the attempt added: the difference from the previous attempt's session total when both ran in the same session (`resume`), and the whole session total when the attempt has a session of its own (`fresh`). An attempt whose `Result` carries no `cost` has an unknown cost: it adds nothing to the task's `cost_usd` or `total_cost_usd` and nothing to the plan's totals, a task or plan budget never stops on it, and `show`, `list` and the arc TUI show the cost as unknown. The attempt's own record says the cost is unknown, and `radian arc run`, `serve` and `start` print one line when a claim starts a command worker for a task or plan with a cost limit: `<task>: worker.command reports no cost; the cost limit does not apply`. arc records the unknown state on the task as `cost_unknown` (decision 5) when the attempt ends, so a later attempt that reports a cost does not turn the task's or its plan's totals into numbers that leave the earlier one out: they stay unknown for the task's life, `reset-budget` does not clear the field, and an attempt that has not ended yet has no cost without being an unknown report.
- **A review stage's cost counts toward the budget.** The `review` stage records the summed cost of its sessions in `review_cost_micros` (a run that reported none records `null`, which adds 0). When arc applies a gate's verdicts for an attempt, it adds that attempt's `review` cost to the task's `cost_usd` and checks the task and plan budgets then; the gate process itself writes no task file (decision 5). When either budget is reached, the task stops in `todo.paused_budget` after that gate, no automatic rework (conflict or review) is written, a plan budget also sets the plan's `auto` to `off`, and only `reset-budget` returns the task to `ready`. A review the gate reruns after a death and a review a `reverify` attempt runs count the same way.
- **A task has a total that `reset-budget` does not zero.** `total_cost_usd` is the sum of every worker attempt and every review stage the task has run. `cost_usd` stays the budget counter and now includes the review stages; `reset-budget` sets it back to `0` and leaves `total_cost_usd` alone. A task file without `total_cost_usd` starts from its `cost_usd` on the next write; arc does not read old verdicts to reconstruct a total.
- `list --json` and `show` give a task's `cost_usd` and `total_cost_usd`; the text `list` prints neither. A plan's `cost_usd` (the sum of its tasks' `cost_usd`, the number the plan budget compares) and `total_cost_usd` (the sum of its tasks' totals) are computed when the plan is read, never stored in the plan file; `list --json` and `show` print both, and the text `list` prints the plan's `total_cost_usd` on its header line.

### 13. The scheduling loop

- **The arc TUI never holds `runner.lock` and runs no pass.** When it opens, and when `R` is pressed, it probes the lock (take and release at once, never creating it). Held: nothing starts, and the header shows `loop ● running (pid <n>)` read from the lock, whoever started that loop. Free: it starts `radian arc serve` with the default interval, from its own executable, in the repository root, as a detached process: its own session (`setsid`, so the terminal's SIGHUP and the TUI's process group never reach it), stdin, stdout and stderr on `/dev/null` (its lines go to `loop.log`), and the TUI neither waits on it nor signals it. The header shows `loop ◌ starting` from the start until a probe sees the lock, and `loop ○ stopped` when none holds it. A start that fails (the spawn fails, or the probe still sees no lock 10 seconds later) is one footer line: the reason, the process's exit code when it exited, and the last `radian arc:` line of `loop.log` when there is one. Starting a loop is the default way arc runs, so no float asks first.
- The TUI shows the loop live from `loop.log`: the newest transition line the file gained since the TUI opened goes to the one-line ticker in the footer, and `L` opens a scrollable view of the last 500 lines that follows new lines while it is scrolled to the bottom. The pages re-read the store every 2 seconds. Reading happens in the runner, not in the page state.
- `q` and SIGTERM close the TUI and nothing else: no float about the loop, and no signal to a loop, whether the TUI started it or not. An attempt a loop left running is reconciled by the next loop, exactly as when `radian arc serve` is killed.
- For a task in `doing.running` the task page's diff is the worker's worktree against the merge base of the remote main and the worktree's HEAD — the attempt's recorded `base_sha` when the merge base cannot be taken, and the source line then says why: `no remote main` when there is no `refs/remotes/<remote>/<main branch>` ref, `no merge base with main` when that ref exists but shares no ancestor with the head — uncommitted and untracked files included and marked `uncommitted` (`live · worktree`), re-read every 5 seconds; after the attempt ends it is the task's own change, from the merge base of the remote main and the selected attempt's head to that head, the range the review stage reads (decision 10), and `base_sha..head_sha` only when the merge base cannot be taken, with the same two reasons on the source line. The diff tab's file list takes at most a third of the diff area's rows, so the selected file's frame keeps the rest, and its last row names the files it shows (`files 13–32 of 40`) when it shows only part of them.
- **The task page's conversation tab shows the selected attempt's worker.** A `radian exec` attempt is its worker journal, found by the session id (decision 4) and read through the attach view: `~/.radian/sessions/<session id>.jsonl`, one weak line while the file does not exist yet, and the 2-second refresh opens it when it appears. A command-worker attempt (decision 7) has no session: the tab shows the attempt's stdout, `runs/<task>/attempts/<attempt>/result.jsonl`, one row per line, oldest first, under a title that names the program the attempt's record names (`execution.json`, else `identity.json`, else the claim's `start.json`; `conversation · <program> stdout`), and follows the file while the attempt runs. The view reads only the bytes appended since the last poll, at most 4 MiB of them per poll, and keeps the newest 4,096 rows, each at most 8 KiB of its line, so a worker that prints without bound cannot exhaust the TUI's memory; the rows before that window are not kept, as the `L` log keeps its last 500 lines. A line that parses as a JSON object shows its `type` value (or `-` when absent) in the weak style and then one summary: the first non-empty string found under `text`, `message`, `command`, `content` or `summary`, at the top level first and then one level down inside an object-valued field (Codex's `item.text` or `item.command`); without one it shows the object compactly. The summary's line breaks become spaces, and the row is cut to the width with `…`. A line that is not a JSON object is shown as it is, cut to the width. A `Result` line shows its `outcome` in the state colour of done (`completed`) or failed (any other value). `j`/`k` scroll and `f` follows the end as they do for a journal, and `[`/`]` switch attempts; a `radian exec` attempt is unchanged.
- `radian arc run` is one pass of the same loop without a TUI. A pass only schedules: it starts a worker or a gate, collects what a worker or a gate left, and moves the state, and it ends in seconds. Waiting for a person, a retry time, a worker or a gate does not keep it running. It writes each transition line and flushes it when the transition happens, and prints the summary when the pass ends.
- **Every loop logs to `loop.log`.** `radian arc run` and `radian arc serve` append every line they print (transition lines, the summary, `radian arc:` error lines) to `.radian/arc/loop.log`, each prefixed with an RFC 3339 UTC timestamp and a space, flushed per line; stdout and stderr stay exactly as they are. At the first line after the file reached 1 MiB it is renamed to `loop.log.1` (replacing an older one) and a new `loop.log` starts, so one old file is kept. A write error on `loop.log` prints one `radian arc:` line once per process and the loop goes on. This holds for every loop, including one started by hand with `nohup`.
- A one-shot `run` starts its work and exits without waiting for it: a worker and a gate are separate processes with their own records. The next `run` collects their results. To keep advancing, use `radian arc serve`.
- `radian arc serve [--interval <seconds>]` repeats that loop: after a pass that ends quiet it waits `--interval` seconds (integer, default 30, 5 to 3600) and runs another pass, until SIGINT or SIGTERM. It holds `runner.lock` for its whole life. It prints the summary only when it differs from the one it printed last. A pass that returns an error prints one `radian arc: <message>` line and the loop goes on with the next pass; the lock and the state stay as they are. **A repeated error stops the loop:** when three passes in a row return the same error text, the loop prints one line, `radian arc: the same error 3 passes in a row; stopping (fix it and start the loop again)`, stops the gates it started the way a stop signal does (it leaves the workers alone), releases `runner.lock` and exits `1`. A pass that succeeds, or a different error, starts the count again. A one-shot `run` still returns its error and exits non-zero. The number `3` is a constant, not a configuration key. The loop, each wrapper and each gate are separate process groups, and a wrapper and a gate treat SIGINT exactly as SIGTERM, so a terminal Ctrl-C reaches only the loop: it starts no new worker and no new gate; a running worker goes on, and the next pass or the next `run` collects it. A running gate (or one whose record is still `started` while it holds the gate lock) gets `[limits] cancel_grace_secs` and is then killed after it has stopped the stage it runs; its record becomes `interrupted`, so the next loop starts it again at once as unverified and counts no death, and a gate that exited without writing any record at all is reported instead and not started again while its inputs are unchanged (decision 10). It prints the summary, releases the lock and exits `0`.
- **A rebuilt binary replaces a running loop's code.** When `serve` starts it records the path of its own executable (`std::env::current_exe()`, resolved once and never read again, because on Linux a replaced file makes it read `… (deleted)`) and that file's identity: device, inode, size and modification time. After each pass, before it waits `--interval`, it looks at the file at that path. When the file exists, is a regular file with an execute bit, and its identity differs from the recorded one, it looks once more after one second and acts only when the second look equals the first. It then prints one line, `radian arc: the radian binary changed on disk; restarting the loop with it`, releases `runner.lock`, flushes `loop.log`, and replaces itself with `exec` of the recorded path with the same arguments, working directory and environment. The pid does not change, so `pgrep` and the pid in `runner.lock` stay meaningful. It starts no gate, stops no gate and touches no worker: a worker and a gate are separate process groups, and the new loop reconciles them exactly as it does after a killed loop. A file that is missing or has no execute bit (a build in the middle of writing it) is ignored and a later pass looks again; a file that changes between the two looks is not run either. When `exec` fails, the loop prints one `radian arc:` line with the error, takes `runner.lock` again (when that fails it exits `1` with a line saying so), records the new identity so it does not retry every pass, and goes on with the old code. A one-shot `run` does not do this. `radian arc mcp` does not do this either: a client that needs a rebuilt `radian` reconnects to its own server.
- **A merge that changed arc's code says so.** When a scheduling pass merges a task (`done.merged`) whose own change touches arc's code, it prints one line: `radian arc: <task> changed arc's code on main; rebuild radian (the loop restarts itself when its binary changes)`. The paths are one list beside the loop: a path under `crates/radian-arc/`, a path under `crates/radian-tui/src/arc/`, or a path that starts with `crates/radian-tui/src/cli/arc`. They come from the task's diff against its merge base, the diff the merge already knows; no network call is added.
- **Two concurrency limits apply to every claim.** A task can be claimed only when the tasks in `doing` of its own flow are fewer than that flow's `[flows.<name>] concurrency` and all tasks in `doing` are fewer than `[limits] concurrency`, the repository-wide total (default `1`). A task's flow is its `flow` field, `default` when absent; a `doing` task's flow is fixed, because the field can change only before the first attempt (decision 6). A running gate takes no slot of either kind.
- **The per-flow limit is on once the file writes a `[flows]` table.** A file that writes no `[flows]` table keeps no per-flow limit for its implicit `default` flow: its tasks count against `[limits] concurrency` alone, so it schedules exactly as it did before flows existed. A file that writes a `[flows]` table, a bare one with no section included, holds every flow to its own `concurrency`, the implicit `default` flow to its default of `1`.
- **Claim order.** A pass claims ready tasks in claim order: the plan's `priority` (`P0` first), then the plan id from small to large, then the task's order in the plan and its `after` list. Priority decides which plan gets a free slot; it never preempts an attempt that is already running. A ready task whose flow is full is skipped, and a ready task of a flow with a free slot further down the claim order is claimed in the same pass, so a full flow never blocks another. A pass never claims, verifies or merges a task of a plan whose `status` is `cancelled`. The verification and merge steps of one pass use the same order, so the stage locks queue in it. `radian arc list` prints plans in claim order, and a plan line and the MCP `list` and `show` documents carry its `priority`.
- **The queue reason names the limit that is full.** `radian arc run`'s summary, the queue line `confirm --dry-run` prints, the task line `radian arc list` prints and `radian arc show`'s `queue_reason` field (the same key in `list --json` and `show --json`) say `waiting for a free <flow> slot` for a ready task whose flow is full (for example `waiting for a free image slot`), and `waiting for a free concurrency slot` when the repository total is full. When both are full, the flow's reason wins. `list` and `show` name a slot only when a limited slot is what holds the task: a task held by an `after` task that has not merged, by its plan's `auto` `off`, by a flow that `config.toml` does not define, or by its own file or its plan having changed outside arc gets no slot reason from them. A file without `[flows]` says only `waiting for a free concurrency slot`, never a flow's reason. `radian arc start` obeys both limits and refuses with a message that names the full limit (`flows.<name>.concurrency` or `limits.concurrency`) and its count; `confirm`'s check for whether a pass would start the task uses the same rule.
- The TUI, `radian arc run` and `radian arc serve` use the same state machine and the same files. A TUI and a loop exclude each other through `runner.lock`: a second loop that cannot get the lock exits.

### 14. v0 scope

v0 runs on one host. Concurrency defaults to 1 task at a time. The v0 gate stages are `commands`, `review`, `human`, and `integration`; `mutation` and `ci` come later. The host fields stay in the file format and are not used.

Named flows are in scope: `[flows.<name>]` is a named bundle of worker settings and a gate profile, and a task's `flow` selects one. A flow's `concurrency` is enforced together with `[limits] concurrency` (decision 13); its `gate_profile` is parsed and validated, and every gate of a task of that flow runs with it. A repository without `[flows]` runs `gate.profile`.

v0 does not have: a resident daemon (`radian arc serve` is a loop a person or the TUI starts and that runs until a signal or an error, with nothing supervising it and nothing restarting it after a stop; it replaces itself only with a rebuilt binary, decision 13); messages to a running worker (corrections go through rework); workers that read or write the backlog or hold the push credential; resume on a different host; more than one scheduling loop; a separate clone per task; automatic rework briefs written by arc, except the conflict-with-main rework and the review rework of decision 9; a gate language; load-based scheduling; more than one worker kind (an attempt's worker is `radian exec` with its flow's `exec_args`, or the command its flow's `command` names); plan branches or plan merges.

### 15. Setup, files, and directories

`radian arc init` sets up arc for one repository. arc does not guess the repository or the gate commands, so without setup `radian arc` and its subcommands refuse and name `radian arc init`.

`radian arc init` runs in the repository. It:

- finds the repository root, the `origin` URL, and the main branch, and writes `config.toml`;
- writes `worker-brief.md` with a short generic default when it does not exist, and never overwrites an existing file;
- creates the layout of decision 5;
- adds the arc paths to `.git/info/exclude` (a local file: `init` never changes a committed `.gitignore`): always `ledger/`, `runs/`, `attempts/`, the two locks, `worktrees/`, and `worker-brief.md`; also `config.toml`, `plans/`, and `tasks/` unless `--track` is given;
- checks the requirements: a stored provider credential (`radian login`), a working push to `origin`, and a working `workspace`-tier sandbox (bubblewrap on Linux); the reachability and dry-run push checks are git calls that talk to the remote, so `[limits] git_remote_timeout_secs` bounds them and a timed-out check is reported like a failed one;
- prints the command that registers `radian arc mcp` with the lead. It does not change the lead's configuration.

The gate commands in `config.toml` are empty or the default profile. The owner writes them.

The `[worker]` table supplies the default worker settings for an attempt and the session shape of every flow:

- `exec_args` (array of strings, default `[]`): extra `radian exec` arguments after the wrapper's fixed ones. It belongs to the `radian exec` worker line only; setting it together with `command` is a config error that names both keys.
- `command` (array of strings, default not set): the program and its arguments of a worker that is not `radian exec`. The first element is the program and the rest are its arguments; no shell. Unset, the worker is `radian exec` exactly as before. An empty array is a config error. A program with a `/` is a path, resolved from the repository root; any other name is looked up on `PATH`, and a program that does not resolve refuses `start`, `run` and `confirm` with exit `3`, naming the flow's `command` key and the program. The key takes effect at the next claim. The environment, the stdout contract and the differences from the `radian exec` worker are in decision 7.
- `rework_session` (`fresh`, the default, or `resume`): the session shape of decision 4. It describes the session id `ARC_SESSION` and the `new`/`resume` value `ARC_SESSION_START` carry for a command worker as well. It stays a `[worker]` key and applies to every flow.

The `[flows.<name>]` table names one flow: the worker and settings a task with `flow = "<name>"` runs with. A name is 1 to 32 characters from `a-z`, `0-9` and `-`, with no leading or trailing `-`.

- `command` (array of strings, default not set): the flow's worker instead of `radian exec`. The first element is the program and the rest are its arguments; no shell. An empty array is a config error, and setting it together with a non-empty `exec_args` in the same flow is a config error that names both keys. A program with a `/` is a path, resolved from the repository root; any other name is looked up on `PATH`, and a program that does not resolve refuses `start`, `run` and `confirm` with exit `3`, naming `flows.<name>.command` and the program. It takes effect at the next claim.
- `exec_args` (array of strings, default `[]`): extra `radian exec` arguments for this flow, after the wrapper's fixed ones. It belongs to the `radian exec` worker line only. The line is checked before `start`, each `run` pass and `confirm` act, and a rejected line exits `3` naming `flows.<name>.exec_args`.
- `concurrency` (integer, default `1`, `1` or more): how many tasks of this flow may be in `doing` at once. A task is claimed only when both this limit and `[limits] concurrency` have room (decision 13).
- `allow_noop` (boolean, default `false`): the value a task of this flow uses at its delivery check when the task's own `allow_noop` is absent; an explicit task value wins (decisions 8 and 5). It is read at the claim of each attempt, so a change takes effect at the next attempt.
- `gate_profile` (string, default the value of `gate.profile`): one `[gate.profiles.<name>]` section. A task of this flow is gated with it: its `stages` and their `required`, its `commands` and `key_commands`, its acceptance rules, and the `before_attempt` steps the wrapper runs; the task's `extra_stages` are added on top. It is resolved when a gate is planned and when the wrapper runs before an attempt, so a change takes effect at the next gate run of the task and the next attempt. A name with no section is a config error when the file is read.

The `default` flow always exists. When the file has no `[flows.default]`, it is built from `worker.command`, `worker.exec_args`, `gate.profile`, concurrency `1` and `allow_noop` `false`. When the file has `[flows.default]` and a non-empty `worker.command` or `worker.exec_args`, that is a config error naming both keys, because one setting lives in one place. A task without a `flow` field uses `default`. A file without a `[flows]` table behaves exactly as it did before flows existed, except that an attempt's records name the flow `default`: its implicit `default` flow has no per-flow limit, so its tasks count against `[limits] concurrency` alone. A file that writes a `[flows]` table holds its implicit `default` flow to that flow's `concurrency` of `1`, like every other flow (decision 13).

The `[gate.review]` table configures the `review` stage:

- `exec_args` (array of strings): the `radian exec` arguments of the review session, after the stage's own arguments. Unset, it is `[worker] exec_args`. It may not repeat an argument the stage sets (`--tools`, `--session-id`, `--workspace`, `--profile`, `--resume`, `--deny-read`, `--mcp-config`, `--yes`, `--output`, `--no-config-mcp`, `-p`).
- `prompt_file` (string): a path relative to the repository root. It is appended to the built-in prompt. Unset: only the built-in prompt.
- `timeout_secs` (integer, default 900): the wall-time limit of one review session; `0` waits forever.
- `concurrency` (integer, default `2`, `1` or more): how many review sessions run at once in the repository. `1` is one at a time.
- `first` is a table for a task's first review (decision 10):
  - `exec_args` (array of strings): the session's arguments, if set, in place of `exec_args`. It may not repeat an argument the stage sets, by the same list, and a repeat is refused as the key `gate.review.first.exec_args`.
  - `timeout_secs` (integer, `1` or more): the wall-time limit of a first review's session, if set, in place of `timeout_secs`. `0` is not accepted here.
  Unset, each key falls back to the `[gate.review]` key.
- `propose_followups` (boolean, default `true`): whether arc proposes the plan's review follow-up task once the plan has no open task (decision 10). `false` turns it off; a plan whose last open task is gone while it is `false` gets no follow-up later.

- **Tracking is the owner's choice.** With `--track`, git sees `config.toml`, `plans/`, and `tasks/`, and the owner commits them when the owner wants. arc never commits them. A checkout or pull that changes a plan or task file is an outside change (decision 5). The ledger, the runs, the attempt records, the locks, and the worktrees are always local.
- The worktrees are inside the repository directory, so they get the repository's trust decision (ADR 0031) and need no extra flag.
- A worktree is created on the first attempt of a task and removed when the task is merged.
- `.radian-worktrees/` is not a radian location. Search (`grep`, `glob`), skill discovery, and `@` completion skip `.radian/arc/worktrees/` and `.radian/arc/gates/` (they skipped `.radian-worktrees/` before). Both are arc's own full-tree checkouts, one per worker task and one per gate stage.

## Constraints and Costs

- arc code is in the repository from the start, so prototype work goes through the gate and Verify.
- In the `workspace` tier, git in the sandbox can write refs, index, and objects (ADR 0038). Linked worktrees share one common directory, so one worker can change another task's branch. v0 detects this before the push and fails the attempt safely. The remote ref is the truth. It does not prevent the change.
- The arc files, approvals included, are in the repository where the lead works. v0 finds outside changes to plans and tasks; it does not prevent a lead from changing arc's files.
- The push credential and the model share an OS user in v0. On macOS the `workspace` sandbox hides an ssh key under `~/.ssh` (ADR 0020 deny list), but it does not block the keychain: a worker can ask the system credential helper for an https credential that the keychain holds. Before v0 runs unattended, the remote must use ssh, or the https credential must not be in the keychain of the user that runs the workers.
- The arc TUI does not embed a terminal. The lead runs in a separate terminal and talks to arc only through `radian arc mcp`.

## Verification

- Backlog: concurrent `add`, `run`, and `cancel` lose no state and claim no task twice. An edit to a task file outside arc stops that task and shows it as changed outside arc; an edit to its approval-looking fields does not approve or merge it. A second `run` that cannot get `runner.lock` exits. A restart continues from the files.
- Attempts: when ssh or the wrapper connection drops while the worker still runs, arc does not start the task again. A result with an old token changes nothing.
- Wrapper: a worker that changes another task's ref makes that task's attempt fail without a push. A crash without a `Result` gives `terminated`, not `reconciling`. An outcome other than `completed` never pushes. A `core.hooksPath` in the worktree does not run during the wrapper's git commands.
- Gate: a verdict counts only for its sha. A moved branch removes it. A new review of the same sha makes an older approval invalid. Task B is verified on a candidate that contains merged task A. A merge fails when main is no longer `base_sha`. With `[gate.review] concurrency` 2, two tasks' reviews run at the same time and each works in its own slot checkout; with `1`, the second waits for the first. A first review runs with the `[gate.review.first]` values and its verdict records them; a rework review runs with the `[gate.review]` values.
- Auto: one plan with three tasks and dependencies runs at level `off` with one start and one merge each, at level `run` to `awaiting_human` for each task, and at level `merge` to `done` with no person. A task that fails its gate `max_auto_rework + 1` times pauses the whole plan and sets `auto` to `off`; a failed reverify attempt is not counted.
- Approval: the MCP tool list contains no tool to confirm, start, merge, reject, change `auto`, or approve.
- Setup: `radian arc init` in a repository creates the files above, and adds the exclude lines once (without `config.toml`, `plans/`, and `tasks/` under `--track`). Without setup, `radian arc` names `radian arc init`. A worker cannot read the arc files outside its worktree. A task branch that changes a file under `.radian/arc/` fails its delivery check. `grep` from the repository root does not enter `.radian/arc/worktrees/` or `.radian/arc/gates/`.
- Commands: `radian arc` opens the TUI. Each subcommand runs and exits with a documented code. `docs/user/` documents every subcommand, option, and file field (`AGENTS.md`).
- TUI and loop: opening the TUI with a free `runner.lock` starts one `radian arc serve` process, which advances a `todo.ready` task of a plan at auto `run` to `review.awaiting_human` and at auto `merge` merges it; quitting the TUI leaves that process running and holding the lock; with the lock held by another process the TUI starts nothing and names its pid; `R` starts one only when none runs; a start that exits `4` shows the code in the footer; a running task's diff shows an uncommitted file. `radian arc run` and `radian arc serve` append their lines to `loop.log` with a timestamp prefix, rotate a 1 MiB log to `loop.log.1`, and print the same stdout. A `serve` whose binary is replaced on disk prints the restart line, keeps its pid and takes its lock again, and leaves a running gate running; a merge whose task changed arc's code prints the rebuild line.
- Priority: of two confirmed plans at auto `run` with one free slot, the higher priority's task is claimed first, and two plans at the same priority keep id order; a priority change takes effect at the next pass and a higher priority does not preempt a running attempt; a value outside `P0`..`P5` is refused with exit `3` and the message lists every value; a plan file with no `priority` reads as `P3` and is written back unchanged; `list` prints plans in claim order.
