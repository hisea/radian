# 可配置压缩阈值 + 压缩后确定性补水

- 状态：idea
- 涉及 ADR：0018（`B` 公式补一个可选上限；摘要结构加确定性的文件清单与补水消息）、0008（配置 schema）
- 来源：`docs/research/2026-10-18-area-deep-dive/3-context.md` §6.9 与 §6.5(a)(c)

## 背景（已量，本机 158 个会话、2026-10-20）

- 1M 窗口的模型几乎不压缩：158 个会话 1 次。每会话最大 prompt p50 32k、p90 362k、最高 637k；69% 的模型调用 prompt 超过 150k。
- 调用延迟随 prompt 增长：p50 从 2.8 s（<50k）到 5.2 s（>300k）。费用因为缓存只差 2 倍（共 $13.41），所以这项的收益是**延迟**，不是钱。
- 代价：阈值设在 200k 时，一个 600k 的会话要压缩约 3 次，每次一个约 100k 输入的摘要调用（几十秒）加失忆风险。所以必须配补水，并且用 A/B 定，不能拍脑袋。

## 待决方向

1. `[compaction] threshold`：token 数或百分比，只调小 `B`，不改 `R`。
2. 补水 (a)：从工具调用里确定性提取读过/改过的文件清单追加到摘要，多次压缩间累积（pi 的做法），不再让模型写 `Files read and modified`。
3. 补水 (c)：压缩后追加一条 System 消息提醒还在跑的后台 job（job 注册表已有）。
4. 补水 (b)（重读最近改过的 ≤5 个文件）看 A/B 结果再定。

## 验收

dogfood A/B（同一批任务，阈值 200k 对比不设）：每次调用延迟 p50、任务总墙钟、压缩次数、压缩后前 5 轮里重复 `read` 同一路径的次数；成功率不降。
