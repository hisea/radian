# 可配置压缩阈值 + 压缩后确定性补水

- 状态：idea（满足下面的「做的条件」就做，且先于 `context-pruning.md`）
- 涉及 ADR：0018（`B` 公式补一个可选上限；摘要结构加确定性的文件清单与补水消息）、0008（配置 schema）
- 来源：`research/2026-10-18-area-deep-dive/3-context.md` §6.9 与 §6.5(a)(c)

## 背景（已量，本机 158 个会话、2026-10-20）

- 1M 窗口的模型几乎不压缩：158 个会话 1 次。每会话最大 prompt p50 32k、p90 362k、最高 637k；69% 的模型调用 prompt 超过 150k。
- 调用延迟随 prompt 增长：p50 从 2.8 s（<50k）到 5.2 s（>300k）。费用因为缓存只差 2 倍（共 $13.41），所以这项的收益是**延迟**，不是钱。
- 代价：阈值设在 200k 时，一个 600k 的会话要压缩约 3 次，每次一个约 100k 输入的摘要调用（几十秒）加失忆风险。所以必须配补水，并且用 A/B 定，不能拍脑袋。

## 做的条件

1. 固定任务集 + journal 指标提取器已落地（`benchmarks/repo-tasks/`、`benchmarks/journal_metrics.py`）：每次调用延迟 p50、任务总墙钟、压缩次数、压缩后前 5 轮重复 `read` 次数、成功率。两项的收益都是延迟，只能在同一批任务上改前改后比。
2. 配置项默认不设阈值，行为不变；只给 A/B 用。
3. 补水 (a)(c) 和配置项同一片做，它们对任何压缩都有用。

**改缺省值的条件**：200k 阈值下任务总墙钟下降、成功率不降、压缩后前 5 轮重复 `read` 不涨。dogfood9「压缩 11 次、一次编辑没有」的空转是已知风险，成功率是硬门槛。

为什么先于 pruning：便宜（配置 + 确定性清单，不动 transcript、不要新 ADR），和 pruning 攻同一个症状。

## 待决方向

1. `[compaction] threshold`：token 数或百分比，只调小 `B`，不改 `R`。
2. 补水 (a)：从工具调用里确定性提取读过/改过的文件清单追加到摘要，多次压缩间累积（pi 的做法），不再让模型写 `Files read and modified`。
3. 补水 (c)：压缩后追加一条 System 消息提醒还在跑的后台 job（job 注册表已有）。
4. 补水 (b)（重读最近改过的 ≤5 个文件）看 A/B 结果再定。

## 验收

dogfood A/B（同一批任务，阈值 200k 对比不设）：每次调用延迟 p50、任务总墙钟、压缩次数、压缩后前 5 轮里重复 `read` 同一路径的次数；成功率不降。

## 2026-10-30 复核：延迟前提在 1M 线路上不成立，收益改按线路算

- 上面「调用延迟随 prompt 增长」的曲线来自 2026-10-20 那批 158 个会话，模型混杂。换成最近 4 天 40 个 worker 会话（opencode-go deepseek-v4.1-flash，4,836 次调用），按 prompt 每 100k 分桶的 p50 延迟是 3.1 / 4.1 / 4.1 / 3.3 / 3.1 / 2.8 s（0–100k 到 500k+）：**平的**。一次摘要调用实测 59.8 s（输出 7,315 token，其中推理 2,587）。把 150k 上限代入这 40 个会话干跑，每一个都变慢（+30 到 +538 s）。实跑一对也一致：TK0220 不设阈值 783 s、0 次压缩；`--context-window 200000`（B = 150k）801 s、1 次压缩，两边 checks 都过。
- 所以在这条线路上，阈值既不省时间也不省钱（超过 200k 的 cached token 一周约 10 美元，扣掉摘要调用剩几美元）。「做的条件」里的 A/B 不再按延迟跑。
- 这项的价值改成两条，都和我们自己的线路无关：(1) 换线路的用户要有地方调。本地推理的 prefill 随 prompt 线性增长，前缀缓存只在完全相同前缀命中；Anthropic 的首字延迟也随未缓存输入增长，长上下文有加价（倍数待核）。pi 把 `compaction.reserveTokens` 和 `keepRecentTokens` 直接给用户设，我们只有 `compaction.auto` 和 `compaction.thinking`。待决方向 1 的 `[compaction] threshold` 照做，缺省不变。(2) 128k 窗口是用户常态（DeepSeek 官方 API、多数本地模型、多数网关），B = 96k。本机 1,033 个会话里 125 个超过 150 步、18 个超过 300 步；把这 18 个放到 96k 预算下干跑，每个要压缩 4–9 次（中位 6），1M 下 0 次。到 2026-10-30 为止压缩代码只有 1 次生产运行（上面那次：150,658 → 39,475，低于 0.75·B 的目标，压缩后 5 步无重读），确定性兜底 0 次。
- 「验收」改成：固定任务集的 4 个短任务加一个长任务（TK0236，305 步），`--context-window 128000` 对比不设，k=2，判 checks、review major、每条压缩记录（`tokens_before`/`tokens_after`/`below_target`、是否 `InsufficientCompaction` 或确定性兜底）、压缩后 5 步内重读旧路径的次数；不判时间，不判 token 总量（同配置复跑差 1.4–1.8 倍，k=2 读不出）。任一失败记为 bug，不是调参。补水 (a)(c) 不变。
