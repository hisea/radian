# 压缩后重读：摘要丢掉文件内容，模型只能重新读

- 状态：idea（待 owner 定方向）
- 涉及 ADR：0018（§摘要、保留尾部 K、回退步骤）、0015（估算）
- 来源：2026-10-31 Mac 轮（deepseek-v4.1-flash，`--context-window 128000`，B = 96k，二进制 6b94155be）

## 现象

4 个短任务 × 2 个 128k 臂 × k=2，共 25 次压缩，0 次 below_target、0 次回退。压缩后 5 步内的 53 次 `read` 里 46 次读的是压缩前已经读过的路径；25 次压缩有 12 次超过预先登记的"≤2 次重读"线。同一任务 128k 臂的模型调用数是 1M 臂的 1.3–2.2 倍，费用约 1.3 倍，尽管 prompt 更小（1M 线路缓存命中高）。摘要提示里已经有 "Files read and modified（每个文件）" 和 "Verified facts (do not re-check)" 两节：路径清单没有阻止重读，模型要改文件就得要内容。

四家都没有解决重读：没有一家把文件内容留下来或重新注入。两家（pi、oh-my-pi）附路径清单，opencode 反而要求少列，codex 不列。oh-my-pi 的 supersede 裁剪处理的是"重读之后旧结果占位"，不是"少读一次"。opencode 遇到过和本地轮一样的摘要雪球，解法是每次把旧摘要重写成一份合并摘要而不是追加。

## 待决方向

1. 压缩时把最近 N 次 `read` 的结果（或最近 N 个路径的最新一次 read）留在保留尾部，不只按 K 切。省重读；K 的分配要变，32k 下留不下几次。
2. 摘要路径只带"最近读过的文件和范围"清单。改动小，但现有清单已经证明不阻止重读，预期效果低。
3. 接受重读，改做异步预判压缩（oh-my-pi、opencode 的做法），把每次 28–78 秒的摘要墙钟藏起来。不省调用，省等待。
4. 128k 下 R 从 25% 降到同行的 10–15%：B 从 96k 到约 109k，压缩次数少一些。要先看 ADR 0018 的 max_tokens 规则怎么配。

方向 1 和 3 不互斥。先等 TK0236 的 8 个运行，看长任务里 6–8 次压缩是否同一形状。

## 验收（方向 1）

- 同一任务 128k 臂压缩后 5 步内重读压缩前路径的次数 ≤ 2；调用数相对 1M 臂的比值下降。
- 1M 窗口行为不变（没有压缩）。
- 变异：保留的 read 去掉 → 重读计数测试失败。
